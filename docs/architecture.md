# Quire 架构

## 全貌


## 两条路径,一条链路

插件是**可选增强**,不是前提。关键在于两条路径最终都汇进同一个剪贴板读取口:

- **路径 A(默认)**:用户自己划选复制。零安装,拿得到片段和原文地址;
  有了地址之后还能由 [`fetch.rs`](#自己抓全文让扩展从必需品变成可选)
  自己把整页抓下来,所以"不装扩展 = 只能存片段"已经不成立了。
- **路径 B(可选)**:扩展对着整页跑一遍 Defuddle,把干净 HTML 和页面元数据写进剪贴板。Quire 那边一个字都不用改。

这样设计换来的是:**扩展不需要任何私有通道**。没有 localhost 端口,没有 native messaging,没有注册表,没有第二个目录要选。用户装扩展的动作从"配置一条 IPC 链路"降级成"加载一个文件夹"。

代价是路径 B 仍然要用户切窗口按 `Ctrl`+`V`(或者开着监控才能一键弹提示)。这是明知的取舍,换来的是零监听端口——对一个大半用户不装扩展的工具来说,这笔账很划算。而路径 A 抓不到全文的那些页面(要登录的、纯 JS 渲染的),现在由扩展来兜。

## 扩展与桌面端的约定

两边只靠一组 `<meta>` 键名通信,键名定义在 Rust 的 `EXTENSION_META` 和扩展的 `META`:

```
quire-version   协议版本,桌面端靠它判断"这份剪贴板是扩展写的"
quire-title     页面标题
quire-site      站点显示名
quire-author    作者
quire-excerpt   页面摘要
quire-published 发布时间
quire-image     封面图
```

外加 `source-url` 带原文地址——这是 CF_HTML 四种取址位置之一,复用现成的解析,不给地址另开一条路。

**统一 `quire-` 前缀不是洁癖。** 用户随时可能复制任意网页,那些页面自带 `author`、`description` 这类 meta;不加前缀,桌面端会把它们当成扩展填的元数据,用户看到作者栏凭空冒出个东西却不知道哪来的。测试 `网页自带的meta不会被误认成扩展元数据` 钉的就是这条。

**空值不传。** 扩展只写非空的键,桌面端也只收非空的值。两头都判一次空,少一个字段传了个 `content=""`,用户还得猜是页面没有还是坏了。

⚠️ **键名漂移不会有编译错误。** 两边是不同语言、不同进程,改了一边另一边照旧编译通过,只是运行时字段变空。所以桌面端侧有测试钉死键名,改的时候两边必须同步。

## 剪贴板捕获:CF_HTML 的四个坑

规范见 [CF_HTML 格式](https://learn.microsoft.com/en-us/windows/win32/dataxchg/html-clipboard-format)。

**偏移是字节,不是字符。** `StartHTML` / `EndHTML` / `StartFragment` / `EndFragment` 都是**字节**偏移。中文在 UTF-8 里占 3 字节,拿字符串索引去切,正文一含中文就错位,而且错得很安静——切出来的 HTML 看着还挺像样。`parse_cf_html` 因此全程在 `raw.as_bytes()` 上切片。测试 `正文含中文时偏移仍然正确` 锁的就是这条。

**CF_HTML 是 UTF-8,不是 UTF-16。** Windows 的剪贴板文本格式几乎清一色 UTF-16,`CF_HTML` 是那个少见的例外。照惯例去解 UTF-16 会得到满屏乱码。

**换行符有三种。** 规范说 header 行可能是 CRLF、LF,甚至是孤立的 CR。所以解析 header 是按"找到第一个不像 `Key:Value` 的行就停"来的,而不是按固定分隔符。

**原文地址有四个可能的位置。** 不同程序习惯不同,挨个兜住,少一个就可能整条回溯链断掉:

1. `SourceURL:` 头部(IE / MSHTML 系)
2. `<meta name="source-url" content="...">`
3. `<meta http-equiv="refresh" content="0; url=...">`
4. `<base href="...">`

只认 http/https,`javascript:` / `data:` 直接丢弃——它们拼进 frontmatter 是安全隐患。四个位置都没有就返回 `None`,**不编造**。前端此时不渲染「打开原文」,总比给个指向空白页的假入口强。

`arboard`(Tauri 剪贴板插件的底层实现)只支持文本和图片,没有 HTML 格式,所以这段是手写 Win32 调用。`CF_UNICODETEXT` 这个常量住在 `Win32::System::Ole` 命名空间下,看着别扭却是 Windows API 的既定事实。

## 信任边界

早期版本的本机 HTTP 服务带来一整类问题:只绑 `127.0.0.1` 并不等于安全,用户浏览器里开着的任何网页都能往那个端口发请求,得靠 Origin 校验挡(详见 git 历史)。现在服务整个删掉了,那类问题连同它的补丁一起消失。**扩展回来时也没有把它请回来**——扩展走剪贴板,不重蹈覆辙。

**新边界是:剪贴板内容一律当不可信输入。** 它来自任何程序——恶意网页完全可以构造一份精心设计的 HTML 让你复制。三道防线:

1. `markdown-it` 配 `html: false`,markdown 里的原始 HTML 不参与解析
2. `DOMPurify` 兜住解析器本身的疏漏(前一道挡不住 markdown-it 自己生成的 `<a href="javascript:...">`)
3. 图片加 `referrerPolicy="no-referrer"`,不把用户读了什么告诉图片服务器

装了扩展等于多信了一方。扩展只读当前页的 DOM、只写剪贴板、**不联网、不发任何请求**,权限只要一个 `clipboardWrite` 和 `activeTab`。它写进剪贴板的元数据照样走上面那三道防线——扩展能给的也只是建议,渲染前一律当外来内容。

**监控默认关闭。** 关着的时候 Quire 一个字节都不读剪贴板。开着时也只做两件事:比对内容指纹、弹提示——**不自动保存、不上传、不留历史**。默认开启的剪贴板监听会把密码、验证码、快递单号一起捕获,太吵,得由用户自己决定。

**监控只通知,不落盘。** 自动存等于替用户做决定;而且开着的时候什么东西都往里灌,用户会失去对"什么进了剪藏"的掌控。

**轮询而不是事件。** 700ms 一次,靠内容指纹去重,变了才 `emit`。Win32 的剪贴板变更通知需要注册窗口消息并在消息循环里泵,复杂度高一档,第一版没做。轮询的代价是提示最多晚半秒,以及一个始终醒着的后台线程——但它不读数据,关着的时候连 `OpenClipboard` 都不调。

## 数据格式

```markdown
---
id: "m8x2k9a4"
title: "本地优先的稍后读"
url: "https://example.com/post/1"
site: "example.com"
author: "张三"
clipped_at: "2026-09-28T14:30:00+08:00"
published_at: "2026-09-20T08:00:00+08:00"
excerpt: "为什么我们还在用云端笔记?"
cover: "https://example.com/cover.png"
tags: []
note: |
  这篇讲的是索引重建,正好接上我上周那篇
  回头对着看
read: false
archived: false
---

正文…
```

### 几个刻意的选择

**Markdown 是唯一真源。** 列表直接读文件,不查数据库。搜索前面挂了一层 SQLite FTS5 索引挑候选,但**索引是纯缓存**:建不出来、坏了、schema 变了,一律退回逐文件扫描,用户只会觉得慢一点。索引里不存任何别处没有的东西,`.md` 永远是唯一真相。

**id 定长 16 字符。** 9 位毫秒时间戳(base36)+ 7 位随机盐。定长是**字典序等于时间序**的前提:变长的话 `m1zz…` 会排在 `m2aa…` 前面,时间序就废了。检索结果按 id 倒序就等于按时间倒序,不必再读 `clipped_at`;在文件管理器里按名称排序也天然是新到旧。

**时间一律 ISO 8601 带时区偏移。** 不存裸 `YYYY-MM-DD`——那东西被 `new Date()` 解析会按 UTC 算,凌晨剪的东西会落到前一天。

**文件名基于 URL 主机名,不采信 `siteName`。** Defuddle 的 `site` 字段在页面缺 `og:site_name` 时会退化成**作者名**,拿它命名会得到 `2026-09-28-xxx-张三.md`。反正主机名能从 URL 算出来,没理由去信一个会漂的字段。`site` 字段仍保留,仅用于显示。回归测试在 `vault.rs`。

**`read` / `archived` / `starred` 放 frontmatter 而不放数据库。** 未读队列、收藏视图直接读文件。索引丢了,数据还在。

**手写 frontmatter 解析器,不引 YAML crate。** 支持的只是 `"..."` 字符串、裸串、`true`/`false`、整数、`[a, b]` 列表、裸键、块标量(`|` / `|-`)、块序列(`-` 开头的行)——不认识的写法当纯字符串,不报错也不丢数据。理由:frontmatter 是我们自己写死的格式,解析器本身就是一份长期契约;用户会在任何编辑器里手改这些文件,十年后还得读得懂。`gray_matter` 停在 2021 年的 0.0.1,不值得为它引一个行为不受控的依赖。

**块序列必须在通用解析之前截住,这是数据丢失的唯一入口。** `parse` 是个**永不返回错误**的纯解析器:读不出来的字段它给默认值,不报错。于是 `tags:` 下面缩进写 `- 重要`(YAML 列表最标准的写法,Obsidian 存出来就是这个形状)时,`parse_value("")` 给出空列表,而列表里的 `  - 重要` 行**没有冒号**,被通用循环 `else { continue }` 跳过——用户文件里明明有标签,Quire 读出来是空的。用户下一次点「标记已读」,`tags: []` 就被写回磁盘,**标签永久消失**,而 `scan()` 的 `unreadable` 机制完全兜不住:它只报解析失败,不报解析错。

所以 `tags` 和 `note` 都在进 `match key` 之前单独截:块序列以 `-` 开头,下一行的 `read: false` 不带 `-`,循环自然停在那里,后面的键不会被吃掉。渲染时统一写成内联 `tags: ["a", "b"]`(Quire 自己产的形状,往返一致);用户手写的块状写法**读得进来,只是下次改别的东西时被规范成内联**——格式变了,数据没少。

**批注用 YAML 块标量(`note: |`),不走引号字符串。** 批注是唯一一块用户从零写的内容,会换行、会带冒号、会带缩进。写成一行 `"第一行\n第二行"` 机器读得懂,人打开 `.md` 只看到一长条带 `\n` 的乱码;块标量任何 YAML 工具都认,人也能直接读——这是「数据是你的」在**格式**上的落点,不是随手挑的写法。

代价是解析器要额外认一种结构,而且**必须认**:用户拿文本编辑器、或者在 Obsidian 里手写批注是常事,读不懂就等于 Quire 成了只能自己写自己读的数据格式。所以 `Frontmatter::parse` 里 `note` 这个键在进通用解析**之前**就被截走——块里的每一行都是内容,不是 `键: 值`,放进通用循环里 `作者: 我` 这种行会被当成新字段,用户的批注就被拆散了。折叠块 `note: >` 不支持,读进来当纯文本。

**未知字段原样保留。** 用户手写的自定义键进 `extra` 兜着,不会因为 Quire 升级就消失。数据是用户的。

**落盘走临时文件 + rename。** Windows 的 `rename` 不覆盖已存在文件,万一盐值碰撞撞了名(概率极低),删掉目标重试,好过留下一个写到一半的剪藏。

**读不出来的文件要报出来。** `scan()` 把解析失败的 `.md` 放进 `unreadable` 列表返回给前端,而不是静默跳过。vault 里的文件用户可能正手动编辑,默默跳过等于让人以为剪藏丢了。

## 抽取:两个必须记住的坑

**`markdown` 与 `separateMarkdown` 互斥。** 只开 `markdown: true` 时,`content` 本身就是 Markdown,`contentMarkdown` 保持 `undefined`;只开 `separateMarkdown: true` 时,`content` 保持 HTML,Markdown 去 `contentMarkdown` 取。同时开两个,结果是读一个永远是 `undefined` 的字段,于是**静默存进一堆空剪藏**。

**两条路径故意用不同的开关,不是笔误:**

| | 谁转换 | 开关 | `content` | `contentMarkdown` |
| --- | --- | --- | --- | --- |
| 路径 A(裸剪贴板) | 桌面端 `clipToMarkdown` | `markdown: true` | Markdown | `undefined` |
| 路径 B(扩展) | 扩展 `content.ts` | `separateMarkdown: true` | 干净 HTML | Markdown |

路径 B 要 HTML,是因为剪贴板得带两种格式:`text/html` 给别的应用用,`text/plain` 装 Markdown 给 Quire。路径 A 只需要 Markdown。桌面端收到 `quire-version` 就知道是哪条,直接用 `text`,**不再过第二遍 Defuddle**——干净内容被再加工一次只会多一处出错的机会。

**`site` 会退化成作者名。** 见上文"文件名基于 URL 主机名"。扩展里也防了这手:`pickSite()` 发现 `site === author` 就退回域名,免得 frontmatter 里写出"站点:张三"。

⚠️ 下面这条是**这个 bug 换来的教训**,值得单独记:Defuddle 的主入口 `defuddle` **不接 Markdown 转换**,`toMarkdown` 在它的 `dist/index.js` 里出现 0 次,在 `dist/index.full.js` 里才出现 1 次。从主入口 import 的话,调用不报错、类型检查也过,但 `content` 拿回来的还是 HTML——桌面端把 HTML 存进 `markdown` 字段,扩展则每次都报"抽不出正文"。**它不跨语言边界,所以 Rust 测试、clippy、构建全都发现不了。**

现在两端都从 `defuddle/full` 导入,并有测试 `产出的是 Markdown,不是 HTML` 钉住(断言结果里不含 `<p>`)。这条测试是验证过的:把 import 改回 `defuddle` 它会真的红。

## 改标志与导出:两条「不许弄坏用户文件」的规矩

`set_flags`(改已读/归档)和 `export_markdown` 都会**重写用户的剪藏文件**,
所以各有几条硬规矩,都由测试钉住:

**只重新序列化 frontmatter,正文原样拼回去。** 正文里的空行、行尾空格、
用户自己加的未知字段,一个字节都不能动。动一样,Quire 就成了那个
"存下来其实是租的"的工具——只是租给了 Quire 自己。

**换行风格按原文还原。** `to_markdown` 只吐 LF;从记事本存的文件是 CRLF。
改一次标志就把它整个转成 LF,等于 Quire 擅自改了用户文件的字节。判据看
frontmatter 段自身有没有 `
`,有就整份还原成 CRLF。

**分隔符后只跟一个换行。** `split` 切出来的 body 自带原来那个空行,
再补一个就等于每次改标志给正文加一行,文件会越滚越胖。

**导出刻意做成纯 Markdown**,不做 zip、不做 json。README 上写着"数据是你的",
那导出的东西就必须脱离 Quire 也能读——用户拿这个文件丢进 Obsidian / Logseq
应该直接能看。做成 zip 就等于把用户的数据再关一次锁。每篇**不带 frontmatter**,
否则拼起来会有十几个 `---` 分隔线,在别的 Markdown 工具里标题层级全乱。
读不出来的文件**跳过而不是整体失败**:一个坏文件不该让整份导出泡汤。

**每周回顾只有一份实现,在前端。** 列表本来就是全量拉回来的,按周分组是纯计算,
没必要为它多一次 IPC 往返。曾经在 Rust 侧也写了一份 `weekly_digest`,结果两边
**时区语义不一致**:Rust 按 `clipped_at` 里存的偏移量算,前端按运行时的本地时区算。
同一篇剪藏在用户换时区后会落到不同的周里——两份实现悄悄跑偏,比没有更糟。已删掉 Rust 那份。

**ISO 周边界不能用「一年里的第几天」硬凑。** `第几周 = (day_of_year + 6) / 7`
一定是错的:归属年由**包含该周星期四**的那一年决定,2026-01-01 是周四,属于
2026 年第 1 周,不是 2025 年第 53 周。判错了用户元旦剪的东西会落到去年年底那栏里。

**归档不能只有一半。** `archived` 这个字段从第一周就在 frontmatter 里,
`set_flags`、前端类型、未读判定全都有,唯独没有按钮——用户根本没法归档。
更要命的是,就算把按钮加上,归档完的东西会**从「未读」里消失又不在任何视图里**,
观感上跟丢了数据一样。所以「归档」是一整件事:正文页的按钮(归档/取消归档,
带 `aria-pressed` 选中态)加上工具栏第四个筛选页。三条不变量由 `list.test.ts` 钉住:
归档过的仍在「全部」里、归档和未读互不包含、两个集合都不含未归档的。

**收藏(星标)走的是另一条路。** 归档是"读完了不打算再看",所以它的按钮只放正文页;
收藏是"这条我反复回来看",那**恰恰是扫一眼列表就想标的动作**,所以列表项上也有。
列表项上那个必须 `stopPropagation`,否则点一下星星会顺手打开正文——用户想标收藏,
结果被扔进阅读页,下次就不标了。

**收藏不是"暂存待读",它和未读是正交的。** 一篇文章完全可以既已读又收藏。
所以 `ListFilter` 里的 `starred` 独立成一个筛选页,不参与"未读 = 未读且未归档"
那套推导;`selectClips` 也不会因为标了收藏就把未读状态改掉——标收藏的时候
顺手把未读清了,用户会以为 Quire 认定他已经读过。

**`starred` 只在为 true 时落盘。** 和 `read: false` / `archived: false` 一样,
绝大多数文件本来就没有这一行,写进去只是噪音。

**按钮放正文页不放列表项。** 「读完了不打算再看」是个读完之后的决定,
不是扫一眼列表顺手能做的判断;列表项上已经有「标已读」了,再塞一个会挤。

**分周按用户此刻的本地时区算**,所以测试必须时区无关。列表测试里的时间戳一律
**不带时区偏移**——`"2026-01-05T00:30:00+08:00"` 在东八区是周一,在 UTC runner 上
折回周日,同一个断言本机绿 CI 红,查起来极费时间。教训只有一条:**时间相关的
测试必须能指定时区,或者干脆别依赖它**。

Rust 侧一共 328 条(桌面端 web 153 条 vitest、扩展 23 条 vitest),`pnpm test` 全跑。两条真实剪贴板往返测试**要求独占系统剪贴板**:别的程序正占着时 `OpenClipboard` 会连续失败,读到的就是空。它们会先探一下可用性,不可用就**带原因跳过**(输出里有一行「跳过 ——」),设 `QUIRE_REQUIRE_CLIPBOARD=1` 可以要求它必须可用。别把跳过当成绿灯——那是**没有覆盖**。

## CI

`.github/workflows/ci.yml`,三个平台矩阵(Windows / macOS / Linux)跑类型检查、前端测试、clippy;**Rust 测试只在 Windows 跑**,因为剪贴板那两个平台之外没有实现,跑出来没有意义。

四步都配了 `fail-fast: false`,一个平台红不影响别的平台报结果。刻意不跑 `pnpm build`——打包验的是"能不能出安装包",不是"代码对不对",那个交给 release。

顺带一提:clippy 走**三个平台**是有意义的。`clipboard.rs` 里的 `#[cfg(windows)]` / `#[cfg(target_os = "macos")]` 分支写错、或者测试代码引了某个平台不存在的符号,只有跨平台编译才现形。

那两条往返测试是整个 `platform` 模块唯一的覆盖。纯函数测试全绿也证明不了 `RegisterClipboardFormatW` 的格式名没拼错、句柄类型没搞混——这类错误在真实调用里才会暴露。两点值得记:

- 用 `Drop` 守卫保证即使断言 panic 也会还原用户原本的剪贴板。
- **必须串行。** 剪贴板是全机器唯一的资源,cargo 默认并行跑测试,不加锁两条测试会互相盖掉对方的数据,表现为"单跑绿、全跑红",而且红的行号每次都不一样。用 `CLIPBOARD_LOCK` 排队。

### 已知:全量并行跑测试偶发堆损坏(根因未定位)

`STATUS_HEAP_CORRUPTION`(0xc0000374)偶发,表现为测试进程直接崩掉、
没有断言失败、没有 panic 栈。2026-09-30 实测:

| 跑法 | 次数 | 崩 |
| --- | --- | --- |
| 全量并行 | 100 | **6** |
| 全量并行(跳过所有执行 SQLite 的测试) | 100 | 4 |
| **全量串行** `--test-threads=1` | 40 | **0** |
| 只跑单个模块(8 个模块 × 12 次) | 96 | 0 |

**触发条件是并行执行。** 两组并行的崩溃率差异不显著(6% 对 4%,Fisher p≈0.7),
所以既不是剪贴板往返(另做了 50 次 × 6 轮 = 300 次重复往返的压力测试,零崩溃),
也不是 SQLite 那几条执行路径。**根因至今没定位**——堆损坏发生在被检测到的
地方和造成它的地方通常不是一处,抓到的现场只有纯函数测试的输出,
`真实剪贴板往返` 两条压根没出现,但"崩溃时没打印它"不能读成"它没参与"。

**现在怎么办:本地和 CI 都用 `--test-threads=1`。** 串行 40 次零崩溃,
而全量 300 条测试串行只要十几秒,慢得可以忽略。**别把偶发的那次当绿灯**——
它不是"这次没出问题",是"这次没测出"。

**顺带修掉一个真 bug**(和这个崩溃没有因果关系,但同属那一类越界读写):
`read_global_bytes` / `read_global_utf16` 里 `GlobalSize` 排在 `GlobalLock`
**前面**。句柄没锁住时那块内存可能正被搬动或换掉,问出来的长度未必对应
锁住之后的内容,拿它 `from_raw_parts` 就是越界。正确顺序是先锁后问大小,
大小不符时还要 `GlobalUnlock` 再返回。

## 标签重命名与合并

标签攒到几十个之后必然烂尾:`rust` / `Rust` / `编程` / `待读` 混在一起,
用户唯一的办法是逐篇点开手改。攒到几百篇那天他就放弃整理了,标签栏从此
变成一坨没人点的垃圾。**所以合并是必须的,不是锦上添花。**

**剪藏库和回收站都改。** 只改一半的话,用户合并完标签,哪天从回收站放回
一篇,旧标签又回来了——他会觉得"合了等于没合"。

**位置原位替换,顺序不动。** 标签顺序是用户自己排的(「重要」在「待读」
前面是他拖的),重排等于替他做了个没人要求的决定。目标标签已经有了就
**删掉那个位置**,不留重复:同一篇里出现两次「重要」,标签栏会显示成
「重要 2」而实际只有 1 篇。

**新标签名先校验再动手。** `validate_tag` 跑在遍历之前,不是扫到一半才
发现名字不合法——那时前面几篇已经改了,用户拿到的是半个改好的库。
长度上限 40 字(`MAX_TAG_LEN`):`clean_tags` 只管清洗字符不管长度,
一个 200 字的标签会一路写进 frontmatter、渲染到标签栏、再渗进搜索索引。
**`set_tags` 和 `rename_tag` 必须用同一把尺子**,一个放行一个不允许,
用户只会觉得这软件有毛病。

**没带旧标签的一篇都不写。** `write_atomic` 改 mtime,而 mtime 变了会
惊动用户的网盘同步,几百个文件同时重传。返回的是「改了几篇 + 哪几篇没
改成」,不是一长串成功列表——合并时绝大多数文件是正常的、只是没带这个
标签,全列进"成功"会把真正需要用户知道的那几篇淹掉。

**入口是右键,不是左键。** 左键那个是筛选,用户天天点,上面挂个
「改这个标签」只会让人多点错一下。

## 打开单篇文件

README 上写着"数据是你的"。兑现这句话不该只能"打开整个剪藏目录"——
用户想拿 Obsidian 看某篇,或者想确认某个附件到底在不在,现在都得自己去
文件夹里按 `2026-09-30-0munof…-example-com.md` 找。

**`clip_file_path` 是这条链上唯一做安全判断的地方,单独抽出来就是为了
能测。** 命令函数要 `State<AppState>`,单测里建不出那个状态;而这个
函数不测就等于把最要紧的一环留在"看代码觉得没问题"的档次上。

**少一道 `is_safe_filename` 就是开了个任意路径穿越**:一个
`../../Windows/System32/xxx.md` 能让 Quire 变成任意文件的启动器。
`打开文件拒绝路径穿越` 那条测试把 `../`、`..\`、`/`、绝对路径、
不带 `.md` 后缀的**逐个试了一遍**——只测 `../` 的话,写的人改成 `..\`
就绕过去了。

**Windows 上打开文件不能直接用 `explorer`**:它会用资源管理器打开
`.md`,而不是交给默认程序。定位才用 `explorer /select,`(注意
`/select,` 后面**不能有空格**,explorer 会把参数当选项解析)。

## 搜索范围

两三百篇之后「搜苹果」会同时捞出讲手机、谈水果、顺带提一句的几十篇。
用户想的是"标题里有苹果的那几篇",这时候给他一个范围开关比给他一个
更聪明的排序有用。

**范围只改候选从哪些字段来,权重是共用的**——但**分数总和必然会变**:
限定标题之后标签那两分就不算了,18 分变成 9 分。这是对的,不是 bug:
两个范围下的分数本来就不是同一个量,拿来互相比没有意义。
(`范围不影响范围内的排序` 那条测试最初断言"分数不变",写完自己一测
就红了——那是个假的不变量,已经换成下面这条真的。)

**真正的不变量只有一条:缩小范围只会少结果,不会多结果。** 一旦范围
条件写反了(比如在 `Any` 那一支里多加了 `OR`),限定查询会冒出宽范围里
压根没有的候选。

**索引那路的范围落在 `WHERE` 的列限定上。** 注意别把列名写进
`build_query` 生成的 MATCH 串里——那边已经被 `WHERE` 管着了,再写一遍
会静默把别的字段搜不了,不报错,就是搜不到(这个坑踩过一次)。

**索引那路"忽略范围"不会让结果变错,只会变慢**:它只负责挑候选,
多挑的那些在打分阶段会因为分数为 0 被丢掉。这是设计在起作用,不是
巧合——所以没有为它写测试,写了也是测一个不存在的正确性风险。

## 记住用户上一次的选择

`settings.rs`。存三样:**剪藏库目录**、**剪贴板监控开关**、**上次打开的是哪一篇**。就一个 JSON 文件,放在系统配置目录下。

**`last_read` 存文件名,不存绝对路径。** 存绝对路径的话剪藏库一挪,这个值就指向一个不存在的地方,而用户以为它还有效。

**打开满 10 秒才算「读过」。** 翻列表时手快的话一篇也待不了这么久,那种「读过」记下来,下次启动停在一篇随手划过去的文章上,用户只会觉得软件在乱跳。

**记下来的那篇后来被删了怎么办?什么都不做**:界面上没有这一篇就回列表,和它还在的时候一模一样。为一篇读不到的文件拦着整个启动流程,那是拿一个边角情况换一次白屏。

**存不进去不报错。** 记住上次读到哪是锦上添花,为一个配置文件失败而弹红条,是在用一条红杠换一个可有可无的便利。值没变也不写——配置每次启动都读,值一样还写只会白白惊动磁盘。

**为什么必须有。** 原来剪藏库路径只活在内存里:用户手动指过一次目录,
**每次重启都要重新指一遍**。剪藏全在那儿,软件却装作不知道在哪。
对一个 local-first 工具来说这是最伤的一处——它卡的不是某个功能,
是**每一次打开**。

**界面语言不在这儿。** 它已经存在 `localStorage` 里(`i18n.ts` 的 `setLocale`)。
同一个东西存两遍,迟早两边对不上,那次"我明明切了语言"会查得很热闹。

**规矩:配置坏了,最坏结果是"回到默认值"。** 这里存的是**偏好,不是数据**——
剪藏在剪藏库里,配置里一个字节都没有。所以读不出来、写不进去、写成乱码,
一律退回默认值继续跑:

- 读失败 → 全部默认(默认目录是 `文档/Quire`,用户照样能用)
- 写失败 → 不报错、不打断,只在返回值里说一句
- 内容不对 → 整个当没这份配置,**而且不删它**,用户还能自己看一眼

**默认必须是"关"。** 剪贴板监控那一条是隐私承诺的落点:配置读不出来的时候,
宁可每次都让用户重开一次,也不能因为配置坏了就开始读剪贴板。
`配置读不出来时监控保持关着` 盯着这条。

**存的时候先写临时文件再改名。** 写到一半断电,留下的是一个完整的旧配置,
而不是半截新配置——半截 JSON 读出来就是全丢。

### 记下来的目录不见了,要说话

`resolve_vault_dir` 返回 `(用哪个目录, 要不要报"不见了")`。

**默默建一个新的空目录是最糟的选项。** 硬盘掉了、网盘没挂、同步盘换了路径,
都会造成这个。这时候 `ensure_dirs` 会把那个目录**建回来**,于是用户看到一个
干干净净的空库、0 篇——而他的剪藏好好地躺在别处。他会以为剪藏全没了,
然后去翻硬盘、翻回收站、翻云同步。

所以这种状态单独记在 `AppState::missing_vault` 里,`info_of` **优先**报它
(排在 `ensure_dirs` 前面,因为下面那个会把目录建回来),
文案说清是哪个路径、并且告诉他剪藏多半还在。

`resolve_vault_dir` 拆成纯函数就是为了能测这条——它决定用户会不会以为数据没了。

## 手动刷新:文件监控挂掉时的救命绳

**`notify` 那套自动监控已经有了**([见上面一节](#文件监控别被自己写的盘触发)),
但手动刷新没删,也不该删:监听器起不来的时候(目录刚被网盘换掉、权限变了、
网盘同步目录上压根不产生系统事件),它是唯一还能把界面刷新的路。

三条路通向同一个 `refreshNow`:工具栏按钮、`F5`、**窗口重新拿到焦点**。
去抖 300ms(切窗口时 focus 有时连着来两三次)。

- `F5` **必须 `preventDefault`**。不拦的话 WebView 会整页重载——
  搜索词、选中项、正文滚动位置全没了,那不是刷新那是重启
- 窗口聚焦这条是**最划算的兜底**:用户"在编辑器改完切回来"是最常见的路径,
  有了这条他什么都不用记。没有的话,他得记得自己按 `F5`——而他不会记得。
  自动监控正常时这条是冗余的,监控一挂它就是唯一的救命绳
- **正在打字时不打断**(搜索框里输入时焦点变化没有因果关系,但结果会跳一下)
- **正在搜的时候刷新不切回全库**。用户输入 "rust"、结果 8 条,随手按一下
  `F5`,列表忽然变成几百条而搜索框还写着 "rust"——他会以为搜索坏了。
  判定在 `refresh.ts`,只有一行,但它是这条快捷键唯一会伤人的地方
- **全仓库只有 `refreshNow` 这一条刷新路径**。另写一套的话,过一阵两条路
  就会分叉(一条清了红条另一条没清、一条刷了回收站另一条没刷),
  而且两条路**看起来都对**,极难查

## 发版:草稿,不是一步到位

`.github/workflows/release.yml`,打 `v*` tag 触发,出四个平台的包,挂成 **draft** Release。

**为什么是草稿。** macOS 的剪贴板实现一次都没在真机上跑过,Linux 更没跑过。
一步到位就意味着第一次跑就把"我们支持四个平台"这句话对外说了出去,而其中
两个是照着文档写的。草稿是不对称的:发出去不费事,收回来费事得多。
想改成一步到位就把 `draft: true` 翻成 `false`,那是你看完装过之后的决定,
不该由我替你按。

**tag 的版本号必须跟 `tauri.conf.json` 对上**,所以第一步是单独一个 job 花 20 秒
验它,而不是合进 build——合进去的话三个平台各跑一遍才报错,白烧 runner。
对不上的后果很阴:包里的版本是 0.1.0,标签写的是 v0.2.0,而**装上去之后
界面上看不出哪里不对**。

**产物收不齐就不发。** 四个平台里少任何一个,release job 直接失败。
macOS 挂了就只剩一个 Windows 包,悄悄发出去等于对外承诺"三个平台都有"。

Linux 固定用 `ubuntu-22.04` 而不是 `latest`:24.04 的 WebKitGTK 大版本变了,
`glib-sys` 编不过。AppImage 打包要从网上拉 linuxdeploy,CI 上偶发失败,
真遇到了就先把 matrix 里 Linux 那行的 `appimage` 去掉,只留 `deb`。

几个本地验过、CI 上更容易翻车的点:

- **产物要拍平加前缀。** 三个平台的文件层级不一样(`target/<triple>/release/bundle`
  vs `target/release/bundle`),而且重名会互相盖掉,所以统一收进一个目录、
  每份前面加平台名。
- **macOS 只出 `dmg`,不出 `app`。** `app` 出来是个**目录**,GitHub Release 挂不上去。
- **`rust-toolchain` 的 `targets` 不能写成 `${{ matrix.target }}`。** 矩阵里
  没给 target 的那两行展开成空串,官方 action 拿到空值会报错——拆成两个
  步骤用 `if` 分开。
- **产物目录用工作区内的相对路径**,不用 `$RUNNER_TEMP`:后者在 Windows 上是
  反斜杠路径,交给 Git Bash 容易出岔子。

## 中文搜索

**索引只挑候选,不打分。** `search_dir()` 持有全部的打分、切片段、排序逻辑;`search_indexed()` 在它前面加一段 FTS5 预筛——先用索引挑出「可能相关」的那几篇,再拿原文走同一套。**两条路必须给出逐条相同的结果**(文件名、顺序、分数、片段),`索引和扫描给出一样的结果` 是这个模块全部的安全网。分叉的后果是用户搜「苹果」时好时坏,而界面上没有任何线索能解释为什么。

**为什么现在上有索引。** 一开始没有:实测 1000 篇、release 构建、每篇都含查询词的最坏情况一次检索 258ms(这个数是**加索引之前**测的),当时判断不值当引 C 依赖。收藏和标签铺开之后单库规模上去,而剪藏这个用法恰恰是「越攒越多、搜得越来越频繁」,扫一遍的耗时又随篇数线性涨。

**索引放在哪儿,以及为什么。** 应用配置目录下的 `indices/<路径的 FNV 哈希>.sqlite`,**绝不进剪藏库**——剪藏库多半开着网盘同步,而 SQLite 文件放进同步目录是冲突重灾区(两边各改一份,同步下来就打架,再下一轮互相覆盖)。文件名用哈希而不是路径本身:Windows 路径里的反斜杠、冒号、中文都得转义,压成哈希没这些问题,切回旧剪藏库时索引还能接着用。哈希是手写的 FNV-1a 而不是 `DefaultHasher`——后者不保证跨版本稳定,哪天 Rust 换了算法,用户已有的索引会集体变成陌生文件、全部重建。

**索引坏了怎么办。** `Index::open` 失败 → `open_or_recreate` 删掉重建 → 还是不行就用内存库。**任何一步都不许让搜索报错**,它只是加速器。schema 变了直接整个删掉重建,不写迁移脚本——为一个缓存写迁移不值当。

**剪藏库和回收站各有一份索引。** 用目录当键。同一个文件名(用户手工拷进去的)塞进同一份索引会互相顶掉,表现是「在剪藏里搜到的那篇,点进去却是回收站里那篇」。

**为什么不用 FTS5 的 trigram。** 它有硬下限:**少于 3 个 unicode 字符的查询匹配不到任何行**,而中文里「苹果」「淘宝」「编程」全是 2 字。trigram 直接废掉一半场景。

**为什么也不上 jieba。** 引入分词库意味着多一个 C 依赖或一大坨词表。二元组已经够用,不值当。

**分词是自研的二元组 + 单字。** 把连续汉字切成相邻二字**和每一个单字**:`苹果手机` → `苹果`/`果手`/`手机` 加上 `苹`/`果`/`手`/`机`。二元组刚好卡在 trigram 那个 2 字下限上,两边对得上;单字是为了让「豆」能搜到「豆包」——只切二元组的话,一字切不出词条,用户打了单字就是零结果,而零结果在用户眼里只有一个解释:搜索坏了。ASCII 单词整体保留并转小写,中英混排能查。

**加了单字之后,`has_token` 必须多一支。** 它原来只有两个分支:二元组走 `contains`,ASCII 走词边界判定。单字会落进 ASCII 那支,而「苹」在「苹果手机」里右边紧跟着另一个汉字,按「左右都不能是字母数字」的规则被判成不是独立词——**于是索引那路(靠词条)能搜到,扫描那路(靠 `has_token`)搜不到,两条路当场分叉**。汉字本来就没有词边界这回事,单字只能按子串判。

**词条要去重。** 加了单字之后「苹果」这一段会同时吐出「苹」「果」「苹果」,撞车是必然的。不去重的话索引里存的就是一串带重复的词条,白白撑大索引文件。

**加了单字之后,那条 258ms 需要重测。** 上面那个数是只有二元组时量的,单字让「所有权」从 2 个词条变成 5 个,扫描那条路每个候选每个字段的 `has_token` 调用数也跟着涨。**重测要 release 构建,本机 debug 下测不出可靠差异**——同一份代码连跑两次能差出一倍(383ms 对 768ms),噪声比效应大得多。在重测出来之前,别拿 258ms 当现状。

**一个已知边界**(不是 bug,别当 bug 查):**不支持拼音**(主动决定,不做)。

**`tokenize()` 返回的是借用入参的切片。** 入参必须比结果活得久。写成 `tokenize(&s.to_lowercase())` 就是把引用指向一个当场析构的临时值——症状极其恶劣:大部分查询碰巧还能中,少数字段(标签/批注/特定正文)莫名其妙搜不到,像随机坏了。`index.rs` 里每处都把 `let lower = ...` 绑成具名变量,就是被这个坑咬过。

**FTS5 表没有唯一约束,`INSERT` 是追加不是覆盖。** 同一篇改一次就多一行,`count(*)` 跟着涨,搜出来会重复。`upsert` 因此先 `DELETE ... WHERE id = ?` 再插。

**MATCH 串里不能再写列名。** 调用那边的 `WHERE` 已经是 `title_tok MATCH ?1 OR ...`,再往 MATCH 串里塞列限定符会静默把标签和批注搜不了——不报错,就是搜不到。

## macOS 剪贴板

macOS 走 `NSPasteboard`,和 Windows 不是同一套东西:

| | Windows | macOS |
| --- | --- | --- |
| HTML 格式 | 自定义 `HTML Format`,头部带**字节**偏移 | UTI `public.html`,直接就是 HTML 片段 |
| 原文地址 | CF_HTML 头部的 `SourceURL` | 独立一份 `public.url` |
| 元数据 | 扩展写在 HTML 的 `<meta name="quire-*">` 里 | **同一套约定**,仍然从 HTML 里取 |

> ⚠️ **这段没有在 macOS 上编译或运行过。** 写它的机器是 Windows。API 签名是对着 `objc2-app-kit` 0.3.2 的源码核过,并且用一个只依赖 objc2 的探针 crate 对 `x86_64-apple-darwin` 跑通了 `cargo check`(那三个 `NSPasteboardType*` 是 `extern static`,取值必须显式 `unsafe`,漏了会报 E0133)。但**"能编译"和"跑起来对"是两件事**,尤其 NSPasteboard 在不同 macOS 版本上的行为差异。发版前必须在真机上验证。

## 构建环境备注

Windows 上构建 Tauri **不需要 Windows SDK**。Rust 1.92+ 的 MSVC target 会在链接时自动生成导入库(已实测 `#[link(name = "user32")]` 在无 SDK 环境下链接通过)。

但 Tauri 仍需要 `icons/icon.ico`——它在 Windows 上要生成资源信息文件(版本号、图标)。这个跟 SDK 是两码事。

## 图片存到本地

**为什么做。** 剪藏的意义是"以后还能看"。图片挂在原站上这件事就不成立:站点关了就全裂,
更糟的是**打开文章的时候图片服务器就知道你什么时候看的哪篇**——和"数据是你的"这句话
直接打架。这个隐私窟窿是产品自己宣传的反面,不能留着。

**代价是明摆着的:reqwest + rustls 让二进制涨了 2.2 MiB(6.5 MB → 8.9 MB,+34%)。**
换的是"存下来的东西以后真的还在,而且读它的时候不联系任何人"。桌面应用多这两兆换这个,
我认为值。reqwest 的 `default-tls` 现在本来就是 rustls,不拉 OpenSSL,三个平台都不用装系统包。

**必须放在后台。** 一篇文章几十张图、几十兆很正常,挡在 `Ctrl+V` 前面等三秒,
这个工具的全部意义就没了。`spawn_blocking` 起线程,下完发 `clip-saved-images`,
界面上明说一句"已剪藏,N 张图片也存到本地了"——**Quire 一直说自己不联网,
现在剪藏这一刻真的连了网,悄悄做和写在脸上是两回事。**

**扫描和改写必须是同一个函数。** 早先各写各的:扫描认得 `<img src=...>`,改写只认 `](url)`,
于是一段 `<img>` 在"找得到要下载"和"替换得掉"之间对不上号。`scan_refs()` 现在同时喂给
`extract_image_urls()` 和 `rewrite_image_srcs()`,两边不可能再跑偏。

**只改图片位置上的那几段,别的字符都不动。** 同理,**下失败的图保持原地址**:
宁可让它裂着,也好过把链接改成一个不存在的本地路径——那样用户连"图原来在哪"都找不回来。
指向 `.png` 的**普通链接**同样一个字不改,`改写不能动到别的内容` 这条测试盯的就是它。

**frontmatter 一个字节都不碰。** 跟 `set_flags` 一样的规矩:只把正文那一段换掉,
前面那截从原文尾部切出来原样拼回去,用户的字段、换行风格、字段顺序都不会被顺带"整理"掉。

**服务器说是图片才存。** CDN 挂掉时常回一个 200 + HTML 错误页,照单全收就是往剪藏库里
塞一堆假 jpg。`Content-Type` 不是 `image/*` 就直接跳过,并把这个失败计入统计。

**删剪藏时图片跟着搬进回收站。** 否则删一篇就在 `assets/` 里留一窝孤儿图,用户既看不出
那是啥,也没法知道删掉的那篇原来长什么样。撤销时一起搬回来。

**两个上限**:单张 20MB、每篇 200 张。都不够的按失败算,但**图片之间不留空洞**——
文件名下标只在成功时递增,不然剪藏库里会出现 `0.png`、`2.png` 这种断号。

## 判重:为什么放在 `Vault` 而不是 Tauri 命令里

同一篇文章剪两次,列表里就是两条几乎一样的,用户得自己认出哪条是新的。
**判重本身是库层的策略,不是界面层的**,所以它落在 `Vault::save_checked()`
而不是 `#[tauri::command] fn save_clip` 里——放命令里就意味着这段逻辑没法测,
而它恰好是最容易改坏的一段(归一化、回收站、force 三条规则互相咬合)。

**认一篇的凭据是地址,不是标题。** 标题可能一模一样,正文可能被网站改过,
地址不会。`normalize_url()` **刻意只做最小的那点处理**:掐掉尾部连续的斜杠,
不动大小写、不动查询串、不排参数。路径大小写敏感、查询串顺序有语义的地方,
一律"归一化"都会把两篇不同的文章判成同一篇——那是**静默丢数据**,
比多存一份重复严重得多。

**回收站里的不算重复。** `scan()` 只看 `clips/` 一层,`.trash/` 是子目录,
天然扫不到。删掉再剪同一篇是"我后悔了想存回来",不是重复。

**判重只读不写。** 已有那篇的正文、frontmatter、换行风格一个字节都不动
(`判重时不碰已有那篇的正文` 盯这条)。顺手"整理"一遍用户自己的文件,
正是这个产品最不该干的事。

**必须给出口。** 文章更新了想重存一份是合理需求,所以 `force` 是一等参数,
界面上就是那个「仍然存一份」按钮。判重要是只进不出,用户就只剩
"自己去剪藏目录里改文件名"这一条路——那不是防重复,那是把活推给用户。

**`Duplicate` 是正常结局,不是错误。** 所以 `SaveOutcome` 是
`#[serde(tag = "status")]` 而不是 `Err`:界面拿到的不是一句报错,
是"库里已经有一篇,叫这个名字",外加一个能跳过去的入口。

## 没有原文地址的剪藏

`Ctrl+V` 是 Quire 的主路径,而**剪贴板里没有链接是常态**:随手复制一段话、一个命令、
一段代码、一个报错栈。早期版本把"缺少原文地址"当成错误直接拒掉,用户按了 `Ctrl+V`
只看到一句报错、什么都没存上——**主路径被堵死,零门槛也就没了**。

现在没有地址的剪藏照存,只是三处做了不同的处理:

- `url` 字段**老实留空**。编一个 `quire:` 之类的假地址看着聪明,实际后果是
  详情页的"打开原文"指向一个打不开的东西,还让"这篇从哪来"变成一句假话。
- `site` 填 `剪贴板`。站点栏空着的话,列表里是 ` · 09-29 16:20` 这么一行,
  看着像程序坏了。
- 文件名后缀是 `clipped`(`slug::site_slug("")` 的既有兜底),
  即 `2026-09-29-m8x2k9a4-clipped.md`。

**判重必须跳过空地址**,这条在 `find_by_url` 里第一件事就返回 `None`:
拿空串去全库比对,第二段随手记的话就永远存不进去了。那是**静默丢数据**,
比多存一份重复严重得多——`没有地址的永远不算重复` 盯的就是它。

详情页的"打开原文"本来就只对 `http(s)://` 渲染,空地址自动就没有那个链接。

## 回收站和隔离区:两级,不是一级

`trash()` 搬文件到 `clips/.trash/`,`restore()` 搬回来,`purge()` **搬到隔离区**,
只有隔离区里的 `forget()` 才真删。分两层是因为**可逆性不同,提示就该不同**。

**为什么从一级改成两级。** 原来 `purge` 是"真删",而产品承诺里写着"误删了能一键
撤销"——这条承诺恰好在伤害最大的地方断了:用户在回收站里点那个红按钮时,
界面只有一句"没有撤销"当护栏。改成两级之后,回收站里那一层随时能翻回来,
真删收敛到隔离区一个 30 天后才发生的自动动作上。

**真删收敛到"过一道手"的地方。** 界面上的两个按钮长得不一样:回收站里是黄色
徽标的「移到隔离区」,隔离区里才是红色的「彻底删除」。摆成同一个样子的
danger 按钮,用户迟早会照着隔离区里那个的力度去点回收站里那个。

**搬走 ≠ 删掉,界面就不能把它抹掉。** `purge()` 之后那一篇仍留在 `scan_trash()`
的列表里,只是 `quarantined` 变成了 true。从界面上抹掉等于骗用户说"没了",
他回头想翻回来连找都找不着。

**保质期由后端下发。** `TrashListing.quarantine_days` 带着 `QUARANTINE_DAYS`
一起返回,前端**不写死 30**。写死的话,改常量那天后端行为全对、没有一个既有
测试会红,只有界面上那句"30 天后自动清理"悄悄变成假话。
`保留期下发的是常量本身` 这条测试就是钉这个的。

**自动清理在启动时跑。** `sweep_deleted()` 扫过期的搬进真删。开软件时顺手做,
不用用户记得点。失败的**不静默**——清不掉的东西还在隔离区里,下次启动再试。

**读不出元数据的文件照样列出来。** 用户可能正拿记事本手动改这些文件。
只显示"解析得动的",他会以为回收站已经空了,而实际上有东西躺在那儿
既看不见也清不掉——那比留着不动更坏。`TrashItem.summary` 是 `Option` 而不是
筛过的列表,就是为了这条。

**`purge` 只在回收站里找。** 少这一层的话,一个拼错的文件名会静默返回成功,
而库里那篇还好端端躺在那儿:用户以为删了,其实没删。同理 `forget` 只在
隔离区里找——否则界面上的「彻底删除」按两下就直接真删了,而用户看到的是
同一个按钮。

**隔离区里已有同名文件不许覆盖。** 用户从备份里把一个文件塞回隔离区,
再点一次「移到隔离区」,覆盖了就凭空少一篇,而这个操作界面上看着像幂等的。

**清空要报清不掉的那些。** `empty_trash()` 和 `forget_all()` 都返回
`BatchReport { succeeded, failed }`,界面必须把 `failed` 显示出来。
"没能清干净"却报一句成功,用户会以为磁盘已经腾干净了。

**能预览才谈得上确认。** 真删是整个软件里唯一没有撤销的操作,
`read_trash_clip()` 让用户删之前能看见内容——看不见就按下去不叫确认,叫闭眼签字。

**回收站不是免费的。** 每条都报 `sizeBytes`,列表头给总量:它占着磁盘,
用户有权知道占了多少。

## 导出:为什么不能只导一个文件

剪藏时图片会下到本地 `assets/<clip_id>/3.png`,正文里写的就是这个相对路径。
只导出一个 `.md`,用户把它发给别人、在手机上打开、在 Obsidian 里看——**一张图都裂**。

而带图剪藏恰恰是最需要「我的数据是我的」这句话成立的那一类:图不在,
那句话在一半用户手里就是假的。所以导出有两个入口:文件夹(带图)和单个文件
(只要文字)。

**按 id 挑目录,只导这次要的那几篇的图。** 拷整个 `assets/` 的话,导三篇
会带上全库的图,用户发出去一个几十兆的文件夹。

**不删目标目录里已有的东西。** 用户会拿现成的文件夹当导出位置,那里面
已经有他的笔记了。

**图片数必须报出来。** 用户把文件夹拷到另一台机器上之后才发现少了图,
那时候他已经没法回头查了。

**正文里的相对路径一个字都不改。** 改成绝对路径在别的机器上一样是裂的。

## 搜索高亮:下标必须是字符,而且是**算出来**的

`SearchHit` 带上 `marks` 和 `title_marks`,是**字符**下标的区间,
前端照着加底色。不往 `snippet` 里塞 `<mark>`:正文里可能有真 HTML,
塞进去之后这份片段既不能当纯文本用,也没法直接进导出文件。

**三个坑,每一个都踩过:**

- **字节下标当字符下标用。** `str::find` 给的是字节偏移,
  `pos - begin - lead` 出来的是字节差,直接当字符数用的话,命中词里
  每有一个汉字就偏一到两个字符。中文正文里这不是边角情况,是常态
- **小写化之后长度可能变。** `mark_in` 先比长度,对不上就不标。
  拿小写版的坐标去标原文,高亮会整体错位,而且只在特定语言下出现
- **`trim` 砍掉的空白要补回偏移。** 不补的话每一篇都恰好偏一点,
  还极难看出是哪儿错了

**前端一律 `createTextNode`,不给 `innerHTML` 开口子。** 标题和摘要都来自
用户浏览过的网页,那里面可能有 `<script>`。高亮是最容易被人顺手写成
`innerHTML` 的地方,所以从函数签名上就不给它这个选项。

**变异验证里抓到过一条真 panic**:`mark_in` 把 `str::find` 的字节偏移当成
字符序号去过 `char_indices().nth()`,下一个切片切在半个字上。
纯英文和纯中文标题都不触发——字节数恰好等于字符数,两套下标退化成同一个值。
所以补了一条用「第 199 篇:讲所有权」这种中英混排的测试,那才是常见的形态。

## 剪藏历史:只放内存里

剪贴板监控弹出提示时,用户只能当场决定存或忽略,**忽略之后什么都没留下**。
他多半只是当时在忙,三分钟后想起来"刚才那个该存",却已经没地方找。

抽屉列出弹过但没存的,能一键补存。**刻意不落盘**:落盘就成了剪藏库之外
的第二套数据源,而那份数据用户既不会去管理也不会去删除。真正存下来的东西
永远在 `clips/` 下的 Markdown 里,那是唯一真相。

**入口不带常驻数字。** 一个一直挂着的「历史(3)」过两天就变成背景噪音,
用户会连点都不点。**没东西的时候按钮整个隐掉**,真需要找的时候他自然会
看见它出现。

**从历史补存走和当场存完全一样的那条路。** 另开一条路就会出现
「补存的没下图片」「补存的没判重」这类只在某个入口下才有的问题。

**`meta` 必须一起存。** 扩展塞进 HTML 的元数据里有标题、封面、作者。
少了它,用户明明是按扩展那条路剪的,补存之后却变成一篇没标题的裸文,
而界面上没有任何提示告诉他少了东西。

## 从别的工具导入:一个规则写一份

`import.rs` 只做一件事:把"别的工具的一行"变成 `Candidate`。
**判重、重新发 id、算文件名、兜底摘要这些步骤全在 `vault::store_imported` 里,
和 Markdown 文件导入共用同一份实现。**

不共用的代价很具体:文件导入会去掉地址尾斜杠、CSV 导入不会,同一篇文章
从两条路进来就被判成两篇——这个错不报错,用户只会觉得"这软件有点怪"。
把 `import_one` 从"读文件"之后那一段拆出来,就是为了让两条路合流。

**CSV 解析自己写,不引第三方 crate。** 只用到 RFC 4180 的一个子集,而坑全在
引号上:字段里的逗号、字段里的换行、`""` 表示一个字面引号。Pocket 的标题
里三种全都有。按逗号硬切会把一篇切成两篇,而两篇都不报错。

**引号只在字段开头有意义。** `他说"好"` 这种不带引号包裹的字段,里面的引号是
字面量;按"遇到引号就切模式"写会从这里开始一路错到行尾,后面整行全解析错。

**Pocket 的 `time_added` 是秒,不是毫秒。** 弄错量级的后果特别隐蔽:每一条都在、
没有一条报错,用户只觉得"这软件好怪"。

**三类结果分开报。** 导进来的、库里已有跳过的、读不出来的。重复不是失败——
用户导进的文件夹里有一半是存过的,那是正常情况。读不出来的**带行号**,
用户回自己的表格里查那一行。

**认不出格式就说认不出,不猜。** 靠内容判断而不是靠扩展名:用户给 CSV 套个
`.txt` 的壳很常见,而 Pocket 的列名足够独特,靠内容认比靠文件头认准。

## 搜索跟着视图走

回收站在界面上是一个独立视图,不是 `clips` 的一个筛选。所以:
`search_dir()` 把检索逻辑和"搜哪个目录"拆开,`search_trash()` 指向 `.trash/`;
前端切视图时清掉 `searchEl` 和 `hits`。搜的却是**库里**的东西的话,
用户会以为"我明明删了它怎么还搜得到"——那等于删了个寂寞。

同理,`r` / `a` 两个快捷键在回收站里直接不响应:它们改的是 `clips` 里的剪藏,
在那里按下去会去改一篇根本不在当前列表里的东西,看起来像"按了没反应"。

## 批量:成败必须分开报

批量最容易出的事就是"**悄悄少做了一半**"。一次改 30 篇,中间有一篇被占用、
有一篇文件名不合法,界面要是只报一句"操作成功",用户回头才发现少了几篇,
而且完全猜不出是哪几篇。所以后端统一返回:

```rust
BatchReport { succeeded: Vec<String>, failed: Vec<PurgeFailure> }
```

`PurgeReport { removed, failed }` 被它取代了——两种形状合一种,少一个类型。

**一条失败不打断后面的。** `record()` 逐条记成败,遇到失败继续往下走。
打断的话,一次改 30 篇在第 3 篇卡住,用户看到的是"改了 3 篇",而剩下 27 篇
到底是没改还是改了一半,他猜不出来。

**批量必须走单条那条路。** `set_flags_batch` 挨个调 `set_flags`,不是先在内存里
算一遍再统一写盘:每个文件的内容都不一样(用户自己加过字段、换行风格也不一样),
只有走同一条路才碰得到「不许弄坏用户文件」那两条规矩。
`批量标志同样走不许弄坏用户文件那两条规矩` 用一个 CRLF + 自定义字段的文件盯着这条。

**批量报告只带回文件名,不带改完的摘要。** 界面因此老实重扫一遍磁盘,
而不是在内存里把标志拼回去——拼错了就是"界面说已读、文件里还是未读"。

### 撤销:批量删除也得有

单篇删除完弹一个撤销按钮,批量删除原来没有。这**不自洽**:一次删 20 篇,
唯一的保险变成"下次少勾两篇"——那不叫保险。确认框也因此从最后一道闸
降级成"别手滑"的提示,它本来就不该替用户确认"这二十篇我真不要了"。

`Vault::restore_batch` 是 `trash_batch` 的对面,同样**一篇失败不打断其余**,
同样把放回来的 `ClipSummary` 一起带回(省得为一个撤销重扫整个剪藏库,
重扫还会顺手 `clearError()` 把刚弹出来的红条清掉)。

**只给真删掉的那几篇一个撤销按钮。** 批量删 20 篇有 2 篇本来就不在列表里
(报的是"没删成"),把没删成的也塞进撤销名单,用户一点撤销,后端就得为它们
各报一次 `vault.notFound`——那两篇压根没被删过,报"放不回来"是在骗他。
`undelete.ts` 的 `undoableFiles` 就是这个判定。

**有失败的时候,红条和撤销按钮要同时在。** 两者是两处 DOM,不打架:
红条(`#warn` 在左栏)说"哪几篇没删成、为什么",toast(底部浮层)说"删了多少、
能退回来"。第一版写成了二选一——"有失败就改用红条,红条上放不下按钮",
结果 18 篇删成的也跟着没了撤销,只是把老问题换了个触发条件。

## 剪贴板:没开窗就读 = 越界读写

`clipboard::tests` 的两条往返测试一直偶发红,还夹着整进程异常退出
(`STATUS_HEAP_CORRUPTION` / `STATUS_STACK_BUFFER_OVERRUN`),单跑永远绿。
以前一律记成"本机环境问题",**那是错的**。

`#[cfg(test)]` 的 `Snapshot::take()` 曾经在**没调 `OpenClipboard`** 的情况下
`IsClipboardFormatAvailable` + `GetClipboardData`。剪贴板是全机器共享的:
浏览器随时一个 `EmptyClipboard`,句柄当场失效,后面 `GlobalSize` 拿到的是
垃圾长度,再拿它 `std::slice::from_raw_parts` 就是越界读写。

生产路径 `read_clipboard()` 一直是对的(Open → 读 → Close),只有测试快照这条路
漏了开窗。补上之后连跑 12 次全绿;修之前 8 次里崩了 2 次。

**教训:** "偶发 + 带内存损坏症状"的测试失败,第一反应该是怀疑自己的 unsafe,
而不是环境。`git diff` 为空只能证明"不是最近的改动引入的",证不了"不是代码问题"。

## 阅读进度:位置是用户的数据

`progress` 存 frontmatter,0–1,`{:.2}` 落盘;**0 不写进文件**——每篇都挂一行
`progress: 0` 是纯噪音,用户打开文件会以为那是个正经字段。

**闸是"值没变就不写",不是"值是 0 就不写"。** 进度是滚动条给的,每抖一下
都来一次。`write_atomic` 是"写临时文件再改名",文件会被整个换掉——mtime 变了、
inode 变了、同步盘会把这轮改动推上去。差不到一个百分点直接返回。

> **这里原来写的是"文件监控也会被吵醒"。那是个不存在的东西。**
> 当时仓库里没有 `notify`,剪藏库上**根本没有文件监控**——被吵醒的是别的
> 程序:用户的同步盘、备份软件、打开着这个目录的编辑器。闸本身是对的
> (少换一次文件就是少惊动一次),但**理由得是真的**。下一个人照着
> "反正有监控会兜着"去做决策,那个前提压根不存在。
>
> 后来 `notify` 接上了(见[文件监控](#文件监控别被自己写的盘触发)),
> 这段推理要重写一遍:现在吵醒 Quire 的**主要是 Quire 自己**——
> 它每剪藏一次、标一次已读、改一次标签都写盘,每一次都跟着一次全量重扫。
> 所以这道闸比当初更该留,只是**理由彻底换了**:不是为了少惊动别的程序,
> 是为了不让自己的写盘把自己吵醒。

反过来,滚回顶部(0)是**真的位置变化**,得记下来:用户重新打开一篇读了一半的
文章又从头看,那"读到哪儿"的答案就该是开头。

**`Value` 补了 `Float` 变体。** 以前没有,`0.42` 会被当字符串存,再写回去
就变成 `"0.42"`——用户文件里的数值每过一次 Quire 就多一层引号。
解析时只认"确实带小数点或指数"的写法,`NaN` / `inf` 一律当字符串,
它们序列化回去会变成没法再解析回来的东西。

**监听器挂在 `detailEl` 上而不是正文节点上**,所以换一篇不会自动摘。
`detachProgress()` 挂在每个重画详情的地方——不摘的话,读第二篇时第一篇的
滚动也会往它自己的文件里写进度。

**但 `detachProgress` 摘定时器之前,得先把那次写出去。** 原来它直接
`clearTimeout` 就完事:用户滚到一半(离 1.5 秒还差 1.2 秒)点开下一篇,
这一篇的进度就永远停在原地——**而进度条还挂在他眼前,显示着刚才那个位置**。
用户不会知道自己的位置被丢了,他只会觉得 Quire 记不住他读到哪儿。

修法是把待写的值从闭包里搬出来,放进一个显式的队列(`progress.ts` 的
`createProgressQueue`)。这么一改,"还有没有没写出去的"就成了能查、能测的
东西,而不是"看定时器还在不在"。定时器到点和切文章都走同一个 `take()`。

**存盘失败原本是个空 `catch`**,理由写的是"记不住进度是小事,不该打断"。
理由站不住:进度条显示着他读到哪儿,存不上他一点不知道,读完关掉下次打开
回到零,他只会以为这个功能坏了。现在失败会弹一句 toast,但**同一场故障
只报一次**——滚动停 1.5 秒就写一次,磁盘抖一下能连着失败十几次,每次弹
一条比不提示还糟(用户会开始无视所有提示)。判官是个三态小状态机
(`progress.ts` 的 `createProgressJudge`):静默 / 该报警 / 刚恢复。

多出来的"刚恢复"是为了**把话说完**。报完错一直不说"好了",用户会一直
惦记着那个提示到底修没修好——下次打开才发现进度条动了,他分不清是
自己读的还是程序存上的。

## 标签:存在 frontmatter 里,不是数据库的一张表

`tags` 字段从第一版就在 frontmatter 里,一直没有界面。这轮把它接上。

**标签是用户随手敲的,所以入库前必须洗。** 洗三样:首尾空白(「 rust 」和
「rust」在标签栏上是两个标签)、重复(同一个词敲两遍,标签栏上出现两个
「待读」,点其中一个只看到一半的文章)、会撑坏 YAML 的字符。**引号尤其
要洗**:用户敲个 `a"b` 进去,`tags: ["a"b"]` 当场解析不出来,这篇剪藏从此
打不开。与其指望用户不敲,不如在门口挡住。

**标签栏只算没归档的。** 标签栏是给「还打算看的那些」用的,一堆归档了的
老标签混在里面,用户点着点着就以为标签乱了。而且同名再算一遍会变成
「重要 7」而实际只有 3 篇还活着,那比不显示更糟。

**筛选跟 `filter` 正交。** 「未读」里只看「待读」是最常见的用法,两个筛子
各管各的,能叠着用。搜出来的结果**不过这道筛**——搜到了却看不见,用户只会
当成搜索坏了。回收站里没有标签这回事,带着标签筛选切进回收站要清掉,
否则出来之后列表是空的,用户以为标签把剪藏弄丢了。

**搜索也认标签**,权重 2(标题 3、正文 1)。用户主动打的标签是明确的意图,
正文里碰巧出现同一个词可能只是顺带一提。

## 批注:唯一一块用户从零写的内容

标签和标题都是**认文章**——标签是给文章贴的签,标题是网站给的(或用户改的)。
批注不一样,是用户记下自己当时的想法。整个 Quire 里只有这一块,写的是
他而不是那篇文章。所以规矩也得不一样。

**存盘必须串行。** 批注是边打字边存的,用户从一篇跳到另一篇,两个保存请求
同时在飞,后回来的那个是**旧**的。照单全收,界面就显示一段用户早就改掉的字,
而文件里是新的——两边对不上,而且用户完全看不出哪儿错了。`note.ts` 里
`pending` 记下存盘期间的新内容,等当前请求落地了再存一次,**永远以用户最后
写的那版为准**。

排队的直接后果:连着改三版只落盘两版。中间那版被合并掉了。这是对的——
用户敲「一」→「一二」→「一二三」可能只花了半秒,把半秒前的中间态也写一次盘
纯属白惊动磁盘:换掉一次文件就是动一次 mtime、动一次 inode,用户的同步盘
和备份软件都会跟着醒。**保证顺序和最终值,不保证一版不漏。**
(原文这里写的是"还会把自己的文件监控吵醒"——同样,那个监控不存在。)

**存失败不冲掉用户写的字,只标出来。** 冲掉等于假装成功过一次;留着字再
标红(`data-state="error"`),用户才知道这段还没存上,重试还是复制走都归他。
一次网络抖动就把编辑器焊死的话,用户后面写的字永远存不进去,所以失败之后
排队的那个版本照样接着试。

**Esc 撤回到后端最后确认过的值,不是撤回到打开时的值。** 失焦和 `Ctrl`+`Enter`
都存,普通回车是换行——批注是多行的,顺手吞掉回车等于告诉用户这里写不了第二行。

**改名和改批注各自独立成模块**(`rename.ts` / `note.ts`),不留在 `main.ts` 里。
`main.ts` 一 import 就 `boot()`,测不了。这两段代码的规矩都不写测试就想不到:
改名那边是「Esc 之后浏览器还会补一次 blur,那次不能当提交」,批注这边是
「保存要排队」。

## 多语言:键在界面,句子在词典,后端只送代号

两本词典,零第三方依赖(一百来条文案不值得为此背一个运行时包)。
中文是源语言,英文跟着补。

**语言判定按 `navigator.languages` 的偏好顺序取第一个认得的**,不是
「列表里有没有中文」。系统首选英文、第二顺位中文的用户,那是他的第一选择,
别自作主张翻成中文。反过来,首选德语、第二顺位中文就该给中文——
不能因为「第一个看不懂」就一路落到英文。

**后端的错误送代号和参数,不送现成的句子。** 原来送的是一句拼好的中文,
英文用户看到的就是一堆看不懂的汉字——那不叫国际化,只叫换了个语种的
界面。参数用**具名**而不是按下标:改文案时调一下参数顺序,按下标取的就
全错位了,而那种错不会报错,只是句子读不通。

`WireError` 只在 Tauri 边界出现,`Display` 那套中文留在 Rust 内部
(测试里断言错误要说人话时还要用)。批量报告里逐条的理由也是同一个形状,
不然一次导入失败二十篇,界面还是甩中文。

**查不到文案就把代号原样返回**,绝不返回空串。空串在界面上是一片空白,
用户只能对着屏幕猜软件是不是坏了;一个看得见的 `vault.notFound` 至少能
让人报出「我这儿显示了一串英文代号」。

`i18n.test.ts` 卡五件事,少一件都会在 CI 里红:

| 检查 | 挡住什么 |
| --- | --- |
| 两边键集合一致 | 少配一条,英文用户看见一串代号 |
| 占位符两边同名 | 英文那句漏了 `{n}`,界面变成「Marked read as  articles」,不报错只是不对 |
| 没有没人用的键 | 改文案留下的旧键,下一个人会以为那功能还在 |
| 界面引用的键都存在 | 拼错一个键名,运行时界面上直接空白 |
| 后端每个错误代号都有文案 | 加了错误类型忘了配文案——**从 Rust 源码抠 `WireError::new`,不从界面扫**,那边的键是运行时拼的 |

### 扩展走的是另一套,故意的

浏览器扩展那边用的是 Chrome 原生 `chrome.i18n` + `_locales`,**不是上面那套
自己维护的词典**。看着像重复,其实是两边环境不同:

- 桌面端在 WebView 里,没有 `chrome.i18n`,只能自己按 `navigator.languages` 挑
- 扩展跟着**浏览器语言**走,装在英文浏览器里的用户就该看英文

强行统一,等于要让其中一边学一个它不需要的挑语言逻辑。

**真正的收益在 manifest。** `name` 和 `description` 写的是 `__MSG_*__`,
扩展列表和商店里显示的名字会跟着浏览器语言变。这是自己维护词典做不到的——
那两处不在任何页面里,没有代码能去查表。

扩展侧的完整性测试(`apps/extension/src/i18n.test.ts`)卡六件事,结构和上面
那张表大同小异,多两条:

| 检查 | 挡住什么 |
| --- | --- |
| 词典**按目录扫出来**,不写死文件名 | 新建一个语言目录却忘了往测试里登记,它就静默地不参与任何检查 |
| `default_locale` 指向真存在的目录 | 少了它 Chrome **直接拒绝加载扩展**,而这个错在构建期完全看不出来 |
| 句子里用到的 `$name$` 都声明过 | 没声明的话,界面上会原样露出 `$title$` |
| **给用户看的句子不许写死中文** | 上面"键都在词典里"抓不到这个 |

最后一条是踩出来的。第一版只有"键都在词典里"那几条,把 `t("error_no_content")`
改回一句写死的中文,**键还是那个键,两份词典照样一模一样,所有检查全绿**——
而结果就是英文用户的图标提示变成一句中文。所以反过来查:**代码里根本不该
出现带中文的字符串字面量**。注释里全是中文(那是给开发者看的,不用翻),
所以先剥掉注释再查。

剥注释用的是自己写的扫描器而不是正则——正则分不清 `"a//b"` 里的 `//` 和
注释的开头。它有个已知的坑:**块注释里不能有"星号紧跟斜杠"那对字符**。
注释里随手写一句词典的通配路径(中间带星号那种)就会把注释提前截断,
后面整段当代码解析。这个坑本文件前两版都栽在里头,头一次是写文档,
第二次是把那句文档原样抄了回来。

## 导入:只读源目录

`import_markdown()` 扫一层子目录里的 `.md`(点开头的目录跳过:`.git`、
`.obsidian` 这些不是笔记)。**只挖一层**:点一次导入把整个网盘同步目录扫一遍,
那不是导入,那是接管用户硬盘。

**源文件一个字节都不写回去。** 源文件夹是用户的,Quire 在这一步只是个读者。

三种源文件:

| 源文件长什么样 | 怎么办 |
| --- | --- |
| 带 Quire frontmatter | 字段照搬,但 **id 和文件名重发**——同一个 id 库里只能有一个 |
| 带别人的 frontmatter(没有 `id`) | **照收**。从 Obsidian 搬来的笔记都长这样,拒收等于把最常见的导入场景堵死 |
| 完全没有 frontmatter | 当普通 Markdown:一级标题当标题,没标题取第一行,站点标「导入」 |

已经在库里的同一篇(按地址判重)跳过并报出来,**不当失败处理**——
用户导进一个存过一堆旧文的文件夹,里面有一半是重复的,那是正常情况。

**剪藏库自己不能往自己里导。** 用户点了"导入剪藏目录"以为能去重,实际得到
一堆换了新 id 的副本,原来的还在原地;反复导几次,库就滚成两三倍了。

**`ImportReport` 把两个文件名分开:** `report` 里是用户源文件夹里的**原名**
(报错要指得准),`imported` 里是落进剪藏库之后的**新文件名**(图片本地化
按它找文件)。混成一个字段的话,报错指着一个用户不认识的带 id 文件名。

**导入的文章照样把图下到本地。** Quire 说自己剪藏时会存图,导入也是剪藏;
不存的话这批文章就成了一个洞——平时看不出问题,等原站关站那天一起烂掉。

## 换库:搬,而不是切

用户换数据目录只有两个正当理由:换了块盘,或者搬去网盘。**两个理由都得
让他几千篇剪藏跟着走**,所以「换目录」这个动作背后必须是搬,不是切。

`migrate_vault` 分三段,顺序一段都不能反:

1. **先把新库建出来再搬**,`new_vault` 用 `Arc` 提前握住。搬一半失败的话,
   用户的配置里还指着旧库——旧库原封不动,他重试一次就行。反过来先切配置
   再搬,中途一崩就是「配置说在新库,新库是空的」,几千篇看着像被删了。
2. **`copy_clips_into` 递归搬 `clips/`,同名文件跳过不覆盖。** 图片在
   `clips/assets/<clip_id>/` 里,跟着正文一起走就自动跟上了。不覆盖是
   有意的:新目录可能已经放着用户自己放的东西,Quire 默默盖掉那才叫数据损失。
3. **`clear_clips` 清空旧库的 `clips/`,而且只在第 2 步整个成功之后。**
   搬家不清空原地,用户换盘想腾出的空间一点没腾出来,旧盘上还躺着一整份。
   但这一步必须排在最后:边搬边删、或者先删后搬,中途失败就是一半在这边
   一半在那边,而用户以为自己只是换了个目录。两条接线测试锁着这个顺序——
   顺序反了不是效果变差,是直接丢数据。

   删完 `clips/` 之后还有一下:**库根空了就连根删掉**。留一个空的 `Quire`
   目录在 `~/Documents` 下面,用户看到的就是"没搬干净"——而那个目录本来
   就是 Quire 自己建的,里面从来只有剪藏。

   但库根很可能**不是** Quire 建的:用户直接把自己的 Obsidian 库选成了剪藏库,
   旁边放着他的笔记和配置。所以判据是**空不空,而不是去猜这目录是谁建的**——
   非空就自己不动手,猜错一次就是删别人的东西。删库根失败也不算失败:
   东西已经搬走了,剩个空目录是碍眼不是数据问题,为它把整个迁移报成失败,
   用户会以为剪藏没搬过去。

   Windows 上还有一层顾虑:文件监听这时候还握着旧 `clips/` 的目录句柄,
   句柄没释放的话那个条目会残留成 pending-delete,库根就被判成非空。
   实测过——notify 开句柄带 `FILE_SHARE_DELETE`,删得掉,库根也跟着没。

**回收站和隔离区不搬。** 它们是删掉的东西,不是用户的资料;搬过去等于
让"删了"变成"没删",还得再删一次。旧库清空时它们跟着一起没——本来就是
已经删掉的东西,没有第二次挽救的必要。

**报数的时候篇数和文件数分开。** 用户问的是"搬过去几篇",而 `clips/` 底下
混着 `.md`、图片和附件;一个数字全算进去,两篇剪藏能报出「搬过去了 26 篇」,
用户第一反应是"我库里怎么凭空多出这么多东西"。所以 `CopyReport` 拆成
`clips` / `assets` / `skipped` 三个数,`.md` 才算"一篇"。

**`copy_existing` 决定搬不搬,前端不给「默认搬」。** 选了目录之后弹的是
三选一(搬过去 / 从空目录开始 / 先不换),**主按钮是「先不换」**——回车和
误触落到的都是它。真按两选一来做,默认的那一边就是丢数据的那一边,而用户
点确认的时候通常没在想这件事。

**主按钮不是主选项,是个刻意的反直觉。** 注释写清楚原因,不然下一个人
会"顺手"把 primary 挪到「搬过去」上。

设置面板上显示的路径读的是 `vaultRoot`,和详情页渲染图片用的是同一个变量。
两处各存一份必然漂移:用户在设置里看到 D 盘,打开一篇图全裂。

## 新用户看到的第一屏

装完打开,是一片空白列表和一个空剪藏库。**这是漏斗最宽的一个口子,
而它不是功能缺失,是缺一句话。**

只给两步,不弹窗、不做向导、不放教程链接。理由很具体:用户试了三次没成
才会去找「怎么用」,在那之前任何引导都是噪音。而这里要解决的恰恰是
**最不容易自己想到的那一步**——大部分人第一次用稍后读工具卡住的都是
「到底存哪儿去了」,不是「存不了」。

**「开启剪贴板监控」做成按钮,不是一句让人去找的话。** 空库这一屏是
用户最愿意点东西的时候,让他自己跑去工具栏找那个小复选框,等于把
最简单的场景做成了最麻烦的。

**只问一次,记在 `settings.watch_asked` 里。** 存这个而不是存
「用户说了不要」:两者界面上表现得一样,但只有前者能让他改主意之后
**不再被问**——用户拒绝一次之后,不该每次启动都被同一个问题拦住。

**用户自己在工具栏拨了开关,也算回答过了。** 那是拿行动回答,再弹一次
是拿他的决定当没发生过。`set_clipboard_watch` 里那句 `watch_asked = true`
就是为这个。

**空态走 DOM 不走 innerHTML。** 原来那句 `list.empty.body` 里带着
`<kbd>Ctrl</kbd>`,靠 `data-i18n-html` 渲染。改成 DOM 之后
`<kbd>` 不再由文案提供——引号带来的风险是真的(标签栏那段是用户
自己起的名字),快捷键的视觉提示不值得用 `innerHTML` 去换。

## 「今天」按日历日,不是滚动 24 小时

差在凌晨那一条。晚上 11 点存的一篇,凌晨 1 点看,按「24 小时内」它
已经过期;而用户凌晨剪藏时想的是「我刚存的那篇」。反过来也一样:
早上 9 点存的,晚上 11 点看,用户会觉得「这都半天前了」。

**基准时间由 `isToday` 的调用方现取**,不缓存——缓存就得给
`selectClips` 加参数,每个调用点都要决定传什么,忘传的那个编译器
不管,界面上就是一片空。

## 大批量下的实测数字

`perfmeasure.rs` 是 `#[ignore]` 的,只在手动跑时执行。**它只打印数字、不做断言**——
它不是回归测试,是一份会过期的测量记录,拿它当门限只会逼着人为了过测试去改数据。

`cargo test --release 实测 -- --ignored --nocapture --test-threads=1`

**2026-10-01 实测(release,Windows,正文按真实文章几百字造)**:

| 操作 | 200 篇 | 1000 篇 | 3000 篇 |
| --- | --- | --- | --- |
| `scan()` 列表刷新 | 44ms | 149ms | 656ms |
| `tag_index()` 标签栏 | 36ms | 201ms | 636ms |
| 搜索(索引路,全命中最坏情况) | 73ms | 281ms | 784ms |
| 导出整个库 | 38ms | 200ms | 623ms |

**结论:全是线性增长,没有数量级的恶化。** 3000 篇时一次刷新 0.6 秒偏慢,但它
不会随着库继续变大而失控,所以不是「现在就得改」的那一类问题。

真要优化,先做的是**让标签栏和列表共用一次扫描**——现在这两条路各把整个库
读了一遍,合起来是 1.3 秒,而实际需要的只是 0.6 秒。**没做**,因为拿不到
留存,先做能测的。

**为什么这些数字不能外推。** 正文长度是按几百字给的,用短正文造的数据会把
文件读的开销压到几乎不见,量出来的数字会比真实场景好一大截——这类实测最
容易骗自己的地方就在这儿。

## 「看起来成功了」是高危缺陷

用户信任一次就毁掉的,不是某个功能慢半拍,而是**他以为成了、其实没成**。
这类地方比缺功能严重得多,所以单独立一条规矩。

判据很简单:**屏幕上的任何一次操作,成功和失败都必须有话可说。**

这一轮审计(2026-09-30)抓到的实例,都是"注释写得很好、实现没跟上"的形状:

| 地方 | 原来 | 现在 |
| --- | --- | --- |
| 块状 `tags:` 列表 | 读成空,下次改标志就把 `tags: []` 写回去,标签**永久消失** | 块序列在通用解析之前截住 |
| 剪藏库建不出来(只读盘/网盘掉线) | `scan()` 返回**空**列表,界面是个干干净净的空库、零红条 | `info_of` 每次真建一次目录,把 `WireError` 带给前端弹红条 |
| 图片没存下来 | 失败数在 `lib.rs` 被 `_` 扔掉;全失败时**连事件都不发** | 事件带 `failed`,一张都没存下来也要说 |
| 单篇删除失败 | `trashClip` 整段没有 `try/catch`,`void` 出去就没人接 | 包了 `try/catch`,与批量那条路对齐 |
| `boot()` 里任一 `listen` 拒了 | 后续监听全不注册、列表永远空、界面上**一条错误都没有** | `unhandledrejection` 全局兜底 |
| 搜索时读不出的文件 | 三个 `continue` 悄悄跳掉。列表视图那边已经报过"有 N 篇读不出",一搜那几篇就没了还不吭声——他明明记得那篇里有这个词,只会以为是自己记错了 | `SearchOutcome` 带着 `skipped` 一起回来,红条点名 |

**全局兜底不是用来替代各处自己的 catch。** 该就地处理的仍然就地处理
(批注存不上要告诉用户**哪一段**没存上),兜底只保证没有哪个错误会彻底消失。
`void someCall()` 这种写法满仓库都是,好处是不用层层 `await`,代价是拒了没人接——
那就得在下面接着网。

**`let _ = e;` 是在藏错误。** 要么把错误带出去,要么在注释里说清为什么可以扔
(`vault.rs` 的 `id_of` 读不到 id 就跳过搬图:那篇没有 id,没有可搬的目录)。
不能既不处理、也不说理由,只留一个下划线。

**"开关开着"不等于"能用"。** 剪贴板监控的开关状态只反映**意图已记进配置**
(`settings.json`),不反映功能可用:别的程序长时间占着剪贴板、剪贴板守护进程
挂了、Wayland 下压根不支持——读剪贴板会永远失败下去,而开关在界面上始终显示已开启。
用户复制十篇,Quire 一次不响,他不会怀疑监控,只会怀疑自己复制的东西有问题,
然后默默把开关关掉,再也不会打开。

(这一段原来就写着"意图已记录",而那时候**一个字都没记**——开关活在内存的
`AtomicBool` 里,每次启动都回到关。现在 `settings::Settings` 存它了,
这句话才成真。文档比实现先走一步,就是下一个人照着它做决策的原料。)

所以记**连续失败次数**,到 10 次就发一次 `clipboard-watch-broken`。
阈值不能是 1:别的程序偶尔占一下剪贴板是常事,那时候报"坏了"是在打扰一个
没出任何问题的用户。报完归零——故障持续下去还会再报,但不会每一次都刷一遍。

**这个数不换算成时间。** 换了平台就不准:Windows 上是事件驱动(系统一改就
通知,压根没有固定周期),别的平台是 700ms 轮询(10 次约 7 秒),
兜底心跳又是 30 秒一次。三种节奏下"够久了"只有一个共同点——
**连续失败了好几次**。

**"不知道"不能写成 0。** 回收站里拿不到文件大小的,发 `None` 不发 0:
"彻底删除"是全软件唯一不可撤销的操作,删之前给的体积承诺得准。界面上写
"删掉能省 0 B",用户会以为自己算错了磁盘占用。总量那一栏同理,只累加量得出来的,
并且说清"至少多少、几篇量不出来"。

## `hidden` 属性:它比你想的弱

用户报"左侧栏有条空白条"。查下来不是谁没写 `hidden`,是**写了也没用**。

`hidden` 靠的是 UA 样式表里的 `display: none`,**特异性极低**——比任何一条
`.类名 { display: … }` 都低。而 `display` 是不管来源的,类规则里写一个
`display: flex` 就能把 `hidden` 顶掉。属性还在 DOM 上,只是不生效了。

这个坑的形状很讨厌:**它按元素发作,不是全局发作**。`.toast` 补过
`.toast[hidden]`,`.batch-bar` 又补过,`.tag-bar` 和 `.batch-tag-panel` 漏了。
后两个的后果是左侧栏底部常驻一条空白条——一个空 `div`,带着上边框和
`background: var(--bg-raised)`,内容永远是空,所以看着像渲染坏了,其实是元素没关掉。
凡是"空容器带边框"的设计,隐藏它的时候一定会撞上这条。

所以改成一条全局规则兜底:

```css
[hidden] {
  display: none !important;
}
```

`!important` 不是保险起见,是**必需**:这条规则写在文件第 31 行,而
`.batch-tag-panel`(74 行)、`.tag-bar`(92 行)、`.toast`(363 行)、
`.batch-bar`(798 行)全在它后面。同特异性时后来者胜,少了 `!important`,
这条规则**当下就是死的**。这也是为什么它不能写在文件末尾——挪到末尾确实
`!important` 就变纯装饰了,但那样就得靠"谁都不动这条规则"来维持。

`css.test.ts` 把三件事钉住:有一条独立的 `[hidden]` 规则(卡住选择器以
`[hidden]` 开头,否则 `.toast[hidden]` 这种按元素补丁会被误判成全局兜底);
凡是模板里带 `hidden` 且 CSS 里设了 `display` 的类都真的管用;以及后面
确实还有设 `display` 的类规则,`!important` 不是白写的。两条断言都做过变异
验证——删掉 `!important` 会红,把规则挪到文件末尾也会红。

顺带一条通用教训:**凡是"给每个元素都要记得加一句"的规矩,迟早会漏。**
要么写成一条规则让漏不掉,要么让测试遍历元素清单去发现漏网的。

## 自己抓全文:让扩展从必需品变成可选

前面那套设计里藏着一个没说破的前提:**路径 A 拿不到整篇**。扩展没装的时候,
用户复制什么就存什么,一篇完整文章根本进不来。而 Quire 自己的立身之本是
「零安装门槛」——让人为了存一篇文章先让一个陌生软件进到浏览器里,
那道坎劝退的人比技术问题劝退的多。

`fetch.rs` 补的就是这一段。Rust 侧用 `reqwest` 把剪贴板里的原文地址抓下来,
交给 **webview 里的 Defuddle** 抽正文——两边各做擅长的一半,不引入第二套
抽取实现。

三个决定值得记下来:

- **正文抽取必须留在 webview。** Defuddle 要 DOM,而 DOM 只存在于 webview 里。
  Rust 那边再引一份 DOM 库,就是同一套逻辑编两遍、以后还要同步两份 bug。
- **抓不到不是故障,是正常结局。** 需要登录、纯 JS 渲染、拦爬虫的页面都会失败。
  所以 `FetchError` 的错误信息**只送代号不送句子**(`fetch.notHtml`、
  `fetch.timeout`…),前端照 i18n 翻;而界面要说的是
  「抓不到全文,已存你复制的内容」,不是弹一条红条。
  **用户已经复制到手的那些字,不该因为他想多存一点而丢掉。**
- **两道大小闸门,一个判据。** 响应头那道(`Content-Length`)必须在
  `resp.text()` **之前**,不然 30MB 已经在内存里了才去问大小;
  读完那道按实读的量兜底,给不给 `Content-Length` 的服务端用。
  两道共用 `size_gate`,写成两处判据早晚有一处被改漏。
  **前提是压缩关着**——`Cargo.toml` 的 reqwest features 里没有
  `gzip`/`brotli`/`zstd`,所以 `Content-Length` 就是正文真身大小。
  哪天开了压缩,闸门得改成读流时按字节掐断,不能靠头。

现在扩展只剩它独有的那部分价值:整页原样、截图、页面自带的元数据。

## 文件监控:别被自己写的盘触发

`notify` 盯着剪藏目录,变了就 `emit("vault-changed")` 让前端重扫。
难点不在接上通知——那是十行代码——而在 **Quire 自己每剪藏一次、
标一次已读、改一次标签都写文件**。照单全收就是每次操作后紧跟着一次全量
重扫,用户看到列表刚更新完又跳一下。

解法是 `watcher.rs` 的 `WriteGuard`:所有写盘方法第一行都调 `note_write()`,
记下"我正在写";写完之后 3 秒内到达的事件丢掉。

三处是踩过才知道要这么写的:

- **用时间戳,不用计数器。** 计数要靠"开始写"和"写完"两次调用配对,
  中间那条路上一旦 panic 或者提前返回,计数就永远停在非零,
  之后所有外部改动都被静默吞掉。症状是「Quire 偶尔不更新了」,极难查。
  时间戳每次都在往前推,不会卡住。
- **按时间窗判,不按路径排除。** 精确排除要 Quire 记得自己写过哪些文件,
  而那个集合和实际写盘是两条独立的路径,中间隔一层就一定对不上。
  漏一条的表现是「莫名其妙不更新」,比晚 3 秒难查得多。
- **自己的事件只丢它自己,不能顺手把攒着的清掉。** 用户改完文件、
  同时在 Quire 里剪藏了另一篇——那次改动会被抹掉,而这一轮再没有新事件,
  它要等到下次手动重扫才出现。`自己写的那条不许清掉攒着的` 盯着这一条。

`is_watchable()` 掐掉三样东西:`.trash/`、`.deleted/`、`assets/`
(跟列表内容无关,而删一篇恰恰是最频繁的操作之一);非 `.md`;
以及 `~$名字.md`、`~`、`.` 开头的临时文件——Word 开着文档时会造锁文件,
`write_atomic` 自己也会先写 `.md.tmp` 再改名,而事件是**改完之后**才到的,
照单全收就是对着一个已经不存在的文件扫一遍整个库。

监听线程用 `recv_timeout` 而不是定频轮询。**没挂着事件时它手上没有任何
东西需要判断**,一秒一醒是纯空转,而这个监控是要整天开着的。

## 剪贴板:事件驱动,但退路必须留着

700ms 轮一次有两个问题,第二个比第一个严重:**延迟**(最坏半秒多)和
**一直在烧 CPU**(监控是要长期开着的,它本来就是零安装门槛的唯一实现路径,
一天下来是十几万次剪贴板读取)。

`clipwatch.rs` 用 Win32 的 `AddClipboardFormatListener`:系统在一个窗口上
发 `WM_CLIPBOARDUPDATE`。关键在于**那个窗口得有自己的消息循环**——
消息只在循环里派发,而 Tauri 的主循环在另一个线程上。

三处是这个方案里真正难的地方:

- **句柄不能放 `thread_local`。** 它是消息循环那条线程建起来的,
  而 `stop()` 是在 Tauri 命令线程上调的。放线程局部的话 `stop()` 读到的
  永远是本线程的初始值(空),函数干完活什么也没停——用户每开关一次监控
  就多留一个线程、一个窗口句柄和一条注册在系统上的监听,而界面上那个开关
  显示的是关着的。`停掉之后句柄就交回去了` 盯的就是这一条。
- **窗口过程里不能读剪贴板。** 读剪贴板要开 OLE,可能卡几十毫秒。
  在窗口过程里读就是让消息队列停摆,更糟的是连 `WM_STOP` 都送不进来——
  用户点关闭监控,那个窗口永远等不到停下的消息。所以窗口过程只往通道里
  敲个门,真正动手的是另一个线程。
- **退路是必须的。** 注册可能失败:会话 0、远程桌面断开、太老的 Windows。
  失败就退回 700ms 轮询——**宁可慢也不能不响应**,监控失效意味着用户
  复制的东西根本不弹提示。即便监听成了,循环里也留着一条 30 秒的兜底心跳,
  万一某条通知没派发到还能捞回来。

`alive()` 问的是"消息循环还在跑吗",不是"句柄非空吗"。循环退出之后句柄还
留在那儿,拿它当存活标志会让一条已经死掉的路径一直以为自己活着。

### 一条测试自己骗自己的例子

`写盘和监控共用同一份记录` 找的是一个多行字符串:

```rust
assert!(!SOURCE.contains("start_folder_watch(
    app.handle().clone(),
    vault.clips_dir(),
    watcher::WriteGuard::new()"));
```

`SOURCE` 是 `include_str!("lib.rs")`——**本文件全文,连测试模块一起**。
而那个多行字符串原样就写在这条断言里,所以 `contains` 必然命中自己,
这条断言恒为假,也就是**它一直是红的**,只是一直没人跑到。
现在改搜 `prod_source()`(切在测试模块之前),并且加了
`prod_source得切在测试模块之前` 盯着这个切点本身。

教训和 `css.test.ts` 那条一样,但更隐蔽:**"在某段文本里找某个字符串"
的断言,当那个字符串就写在断言里时,结果和被测代码长什么样无关。**
凡是用 `include_str!` 扫源码的测试,搜索范围都得先切掉测试模块本身。

### 测 AppHandle 的那条测试为什么默认不编译

`真起真停之后不算活着了` 碰 `AppHandle`。而 `AppHandle` 一进测试二进制,
本机 link 出来的 exe 就在**加载阶段** `STATUS_ENTRYPOINT_NOT_FOUND`,
连 `running 1 test` 都来不及打印,整轮四百多条测试跟着一起归零。

`#[ignore]` 躲不掉这个——它只是不执行,代码照样被链接进去。只能靠 feature
让它**根本不编译**:

```bash
cargo test --features live-clipwatch -- --ignored clipwatch
```

这个毛病是测试构建的,不是被测代码的,所以别拿它当"这条逻辑有问题"的证据。

## 图片和视频:必须在交给抽取器之前救

真机反馈「图片视频没有链接」。顺着链路查下来,是三个各管一段的环节
互相踩空,不是某一处的 bug:

- **懒加载变体**。现代页面把真地址藏在 `data-src` 系列属性里。Defuddle
  自己会认 `data-src` 和 `data-srcset`(写探针实测过,不是猜的),但
  `data-original` / `data-lazy-src` 这些老站变体它不认——拿不到地址,
  它的 img 规则就把**整张图丢掉**,连 alt 都不留。
- **视频和嵌入**。turndown 会把 `<video>`/`<iframe>` 原样保留成 HTML,
  而 Quire 渲染侧 `html:false` + DOMPurify 两道防线(刻意不拆,剪藏是
  不可信输入)只会把它们转义成一行字面代码或整个洗掉。
- **YouTube 嵌入**。Defuddle 自带规则把它转成 `![](视频页面地址)`——
  那是页面地址不是图片,在 Quire 里是必然裂掉的图。

修法在**抽取之前**:预处理把懒加载地址提升成 `src`、把 `srcset` 拆掉
(里面的候选没经过绝对化,留着只会让抽取器从里面拿相对地址)、相对
地址转绝对、视频/音频/iframe 换成一条可点的链接。链接是 Markdown 时代
处理媒体的通用答案:渲染侧两道防线一根手指都不用动。

扩展和桌面端各有一份同样的预处理(跨包不共享代码,两边各有测试锁行为)。
桌面端 `clipToMarkdown` 是行为测试端到端锁的;扩展侧是源码断言——
而且变异验证当场抓了个空:初版断言只查「调用了预处理」这个文本存在,
把调用改成死分支照样绿。收紧成「`const prepared =` 接住、`new Defuddle(prepared,`
消费」之后,删掉调用块才真的红。**断言要锁的是数据的流向,不是关键词的出现。**

## 链接:出去的路只有一条

详情页**就是** Quire 的整个界面。在正文里点一条外链,WebView 的默认行为
是把 `tauri.localhost` 导航成那篇文章——用户眼里的现象是「Quire 没了,
关掉重开才回来」。所以链接的处理只有一个策略:**整条下放给系统默认
浏览器**。

前端在 `document` 上挂一个点击委托:命中 `a[href]`、scheme 是
http/https 就 `preventDefault()` 然后调后端的 `open_url`。**委托必须
挂在 document 上**——正文每次重画都换一批节点,挨个绑监听既漏新节点
又忘解绑旧节点,只有委托是一份且永远在。

scheme 白名单在 **Rust 侧**,不是前端。这不是格式检查,是安全闸:
`explorer <url>` 走 ShellExecute,给什么执行什么——`file:///` 能打开
可执行文件,自定义 scheme 能唤起任意注册过的程序。剪藏正文里的链接
是不可信输入,所以除了 `http`/`https` 一律拒,拒了给界面一个代号,
让用户知道「这个地址打不开」而不是「点了没反应」。

## 搜不到:那个时刻整个产品就靠它了

一个稍后读工具的核心承诺是「你存过的东西一定找得回来」。**搜索一旦失灵,
整个产品就失灵**——而用户不会去 debug,他只会默默不再搜,然后慢慢不用了。
所以「搜不到」那一屏是这个产品最需要帮忙的一刻,原来的实现是两句废话:
「没找到」「换个词试试」。

三样东西加上去,都不是新机制,是把已有的那条路用对:

- **差一个字的容错(`search_loose`)。** 编辑距离 ≤ 1,单字不参与,
  至少一半词条要命中。**只在标准搜索一条都没命中时才走**——结果少说明这个
  词是有效的,用户要的是更准不是更多;那时候再塞一批"差一个字"的进来,
  是拿他本来找得到的换他本来就找不到的
- **最近搜过的词。** 用户搜不到的时候想不起当初搜的那个词,这比换十个词都快。
  存进 `settings.json` 而不是只放内存:「再搜一次上次搜的」必须跨重启有效
- **提醒放宽范围。** 把范围限成"只看标题"却搜了个正文里才有的词,
  是搜不到的头号原因,而用户自己多半没意识到限了

三处判定值得单独记:

```text
**为什么是编辑距离 1,不是 2。** 不是算不动,是**算了有害**。差两个字的两个词
多半根本不是同一个词,凑到一起用户会以为 Quire 在胡说。而差一个字才是"手滑"
最可能的样子。

**为什么要求一半词条命中。** 只要"命中一个"的话,长查询几乎**每一篇**都能凑上
一个:「扫地机器人」切出「扫地/地机/机器/器人」,而正文「换了新手机」里有个
「手机」——「地机」和「手机」就差一个字。那不是近似命中,那是全库。

**为什么近似结果一律不高亮。** 用户打错的是哪个字,我们并不知道。标出「手机」
而他搜的是「手记」,等于告诉他 Quire 认定他没打错字——那他更不会相信这批
结果了。
```

### 繁简算命中,那是故意的

「手機」和「手机」只差一个字,所以算命中。**用户习惯打繁体就该找得到简体
的内容**,反过来也一样。编辑距离分不出繁简,而这里不需要分——差一个字就够。

## 回来:数字是「拉」,不是「推」

打开 Quire 的理由有两个:「我又想存点东西」和「我欠了自己 8 篇」。
第二个理由以前不存在——「未读」筛选一直在,可用户得自己点进去才知道欠了几篇。

所以「未读」按钮上写了个数字。**它必须是个数字而不是通知**:通知是「推」,
用户没要求就被推着走,用两次就烦了,烦了就关掉,再往后连开都不开了。
一个数字是「拉」——打开时自己看见,要不要看是他的决定。**0 就不显示**,
挂个 0 只是让人多看一眼。

搜索进行中不显示这个数字:搜索框里那几篇是**搜出来的**不是「全部」,
用户搜「苹果」看到「未读 3」,会以为库里只剩 3 篇没读。

`renderUnreadBadge` 走 `list.ts` 的 `unreadCount()`,不在 `main.ts` 里自己数一遍。
两边各写一份判定的话,改了一处另一处没跟上,用户看到的「未读 8」点进去
却是 11 篇——**那种错任何单测都抓不到**,因为两边各自都对。

## 补全全文:几周后的第二条路

剪藏那一刻抓不到网页,只存了用户复制的那一小段。**几周后他想起那篇文章想看
全文,旧版本里他只能删了重剪一遍**——而重剪多半还是失败。

`set_body` 的规矩只有一条,但很硬:**只换正文,frontmatter 一个字不动。**
标签、批注、已读、阅读进度都是他在这篇上花过时间的证据,一个"重试"把它们
清掉,那不是帮忙,是**用一次点击抹掉他一段时间**。

还有一条:**新正文更长才写。** 抓回来的万一比原来的还短(页面改了、抽出来只剩
个壳),拿它覆盖掉他已有的内容是净损失,那就原样不动。

抽取仍然在前端,跟剪藏那一步**同一条路**(`clipToMarkdown`)。另开一条抽取路径
等于给同一件事写两份实现,迟早不一致——而用户看到的现象是「重试补出来的正文
跟剪藏时长得不一样」。

## 还没做完的:数当下的文件,不记事件

图没下下来、抓取失败、文件读不出,过去都是一次性提示,弹过就没了。用户永远
不知道「我这一周有多少东西没存全」——而「数据在你手上」这句话,在带图剪藏
导出成一片裂图的时候就是空的。

`library_status` 的第一原则是**数当下的文件,不记下来的事件**。记"当时失败了几张"
的话,用户后来自己把图补上、换了剪藏库,那条记录就过期了——而**一份过期的账
比没有账更坏**:它会让用户以为还有图没处理,或者反过来。

三样都空就是什么都没欠,界面上就**不摆那个入口**。一个永远在那儿、点进去写着
「一切都好」的按钮是给人添乱的。

两处判据必须与其他地方一致,否则用户看到的是"有的篇能补有的不能补",
完全摸不着规律:

```text
**只数图,不数链接。** `![图](u)` 和 `[链接](u)` 在 `](` 之后长得一模一样,
区别在 alt 文本前面那个 `!`。认错了就会把正文里每一个超链接都数成"没存好的图",
而这一栏的全部意义就是可信。

**「没抓到全文」和详情页那个按钮同一条判据。** 有能抓的地址、正文短于 500 字。
两处各写一份的话迟早有一处被改漏——改漏的后果就是"时灵时不灵"。
```

## 两条测试通用的教训

这一轮又有两条测试自己骗自己,成因不同:

**`SOURCE` 把自己也包进去了。** `写盘和监控共用同一份记录` 找的是一个多行字符串,
而那个字符串原样写在断言里,而 `SOURCE = include_str!("lib.rs")` 连测试模块
一起包。凡是用 `include_str!` 扫源码的测试,搜索范围都得**先切掉测试模块**。

**`toContain` 是子串匹配。** `expect(css).toContain(".clip-fuzzy")` 在规则被改名成
`.clip-fuzzy-typo` 时照样通过——而那个类名在模板里一个都没用,界面上就是一片
裸的。断言选择器得匹配**选择器本身**(`\.cls\s*[{,]|$`),不是匹配一段文本。

还有一条跟工具无关但每次都踩:**变异脚本数"通过了多少"会数错。** vitest 失败
时打的是 `Tests 1 failed | 190 skipped`——**一个 passed 都没有**;
Rust 失败时是 `0 passed; 1 failed`。按 `passed` 找会得出"没跑起来",
把一次**有效的红**误报成无效——而"脚本没测出来"和"测试没兜住"是两回事。

## 编辑期间的冲突:停下、说话、让用户选

详情页在编辑时有一个**静默吃数据**的场景,一直到这一轮才堵上:

```text
你打开一篇,写了半句批注(还没失焦,所以还在输入框里)
这中间去 Obsidian 改了正文
回来接着写、失焦自动保存 —— set_note 读的是磁盘上此刻的文件,
它自己不知道输入框里的内容是几秒前的。
丢的不只是那半句批注:正文也会一起被写回成旧的那份。
```

`ClipContent` 里多了一个 `stamp` 字段:**读这篇时磁盘上那份的指纹**。
改标题、写批注、补全文的时候把它带回去,后端写之前比一次,对不上就
`VaultError::ChangedElsewhere`,一个字都不写。

**为什么是指纹不是 mtime。** mtime 的粒度是 1~2 秒(取决于文件系统),
而"你在 Obsidian 里改了、我这边隔几百毫秒失焦保存"这种操作,
那一次 mtime 压根没变——冲突就漏了。指纹是内容的,改一个字节就变。

**指纹只算用户手写的那几项:标题、批注、标签、正文。** 这一条是踩出来的:
第一版哈希的是整份文件文本,而 `set_progress` 滚动一下写一次、
`read` 随手就标——都是 Quire 自己在写。用户开着详情页边读边写批注,
中间滚动了两下,下一次自动存批注就撞上"被别处改过",而外面根本没人碰过。
**天天喊狼来了的守卫,用户第三次就学会直接忽略它,那时它挡住的和没装一样。**

**冲突了怎么办:先停下,再问。** 默认动作是"不写"。自动帮用户合并看着像
贴心,实际是在他没参与的情况下决定谁的内容该活下来。两个选择都给:

- 「读最新的,我的改动不要了」——主按钮,通常也是更常见的那一半
- 「用我这份覆盖回去」——他确实知道自己写的是什么的时候,**这才该赢**

"覆盖回去"重试时**不带指纹**:带了就是拿几秒前那份盖掉刚敲的,那正是这个
守卫要拦的事。冲突得由用户显式解除,不能自动解除。

**写成功之后要换新指纹。** 不换的话,下一笔改的还是这一篇时会拿
**自己刚写的那份**去跟旧指纹比,自己跟自己冲突——第二次保存起就再也存不进去。
四处读取点(`openDetail` / `openDetailNow` / `refreshOpenDetail` / 换语言重画)
和两处写成功点都归了位,`conflict.test.ts` 逐个点名盯着。

**批注冲突时绝不碰输入框。** 用户半句话还在里头,重画一下就没了,
而他这半句正是最该留住的东西——只有用户自己点「读最新的」才重画。

## 批量改标志、打标签也能撤销

批量删除早就有撤销了,批量标已读 / 归档 / 打标签没有。这**不自洽**:
一次动 20 篇,唯一的保险是"下次少勾两篇"。

难点在于**批量命令是"设成 X",不是"翻一下"**。撤销要是也发一次
`read=false`,那用户本来就标了已读的三篇会被翻成未读——撤销一次反而
造出新错,而且他根本无从察觉。所以动手前先把每篇**当时是什么**拍下来
(`snapshotClips`),撤销时按那张快照写回去。

**快照只拍这次真要改的项。** 「只标已读」不该把归档状态也拍下来,
否则用户在这中间手动归档过一篇,撤销会拿这个旧值把它盖掉——
凭空造出一个他从没做过的改动。`ClipSnapshot` 的字段因此全是可选的,
没拍的项在协议上就是"别动这一项",而不是"改成 false"。

**撤销逐篇发,不合成批量。** 批量命令只能"全设成同一个值",而快照里每篇
的旧值不一样。二十篇多二十次 IPC 也就几十毫秒,而"撤销之后比撤销之前更乱"
是用户再也不信这个功能的开始。

**只有真改成功的那几篇才给撤销。** 给没改成的篇一个撤销,用户点下去会
看到"已撤销",而实际上什么都没变——他会以为这条路验过了,于是下次更敢
批量操作。

## 列表一次画多少

全库一次性铺进 DOM 的日子结束了。每一条剪藏是十来个 DOM 节点加两三个
事件监听,库里上千篇时一次全画出来,滚一下就是几千个节点一起参与布局——
**而用户存到几百篇正是这个软件成功的样子,不该在那一刻变卡。**

`listWindow(items, limit)` 是那道闸,`LIST_PAGE = 200` 是它的档位。
四条渲染路径(主列表、每周、搜索命中、回收站)走同一个函数。

**`limit` 是"最多画几条",不是一个页码。** 页码语义下往回翻得判断当前在
第几页,判断错了列表就跳一下;而用户点「显示更多」想的是"接着往下看"。

**换视图必须把额度拨回 `LIST_PAGE`。** 换筛选、换标签、换搜索词、
从统计面板点标签,四处入口都要拨。忘了拨的话,用户在上一个视图里点过两次
「显示更多」,切过去第一眼看到的是一个已经翻了两屏的列表——而他根本还没翻过。

**界面必须说得出"还没画完"。** 少了底下那条「还有 N 篇」,上限就成了一次
静默的数据丢失:用户存了八百篇只看到两百,会以为剩下的没了——
而那是这个软件最不能被怀疑的一件事。

**截断和键盘、全选是同源的。** `visibleFilenames` 读的就是画出来的那些,
所以看不见的既点不到,也不会被 `Ctrl`+`A` 圈进去拖去删掉。

### 实测数字(前端)

`clip-item.perf.test.ts` 量的是真代码(`clipItem` 为此从 `main.ts` 抽成了
`clip-item.ts`,那个文件一 import 就 boot,逻辑留在里面就永远量不了)。

**2026-10-01 实测(jsdom,Windows,2000 篇,三轮取最小)**:

| 操作 | 耗时 |
| --- | --- |
| `selectClips` 筛一遍两千篇 | 0.9–1.2 ms |
| 画 200 条 | 52–70 ms |
| 画全部 2000 条 | 556–566 ms |

**jsdom 不是浏览器,绝对值不能外推**(它造节点比真实 WebView2 慢),但比例
可以直接看:**画满比画一屏贵一个数量级**,而这一条就是上限存在的理由。
测试里的门限因此放得很宽(3 秒),只为挡住数量级的劣化,不做精细回归。

**量之前必须先热身。** 第一版没热身,量出来"库 200 篇"比"库 2000 篇"还慢
50%——看着像悖论,其实是先跑的那个在替后跑的付 JIT 的账。`drawMs` 现在
先空跑一轮不计,再量三轮取最小值(异常值只会往上跑,GC、抢 CPU 都是)。

另一条比耗时更要紧的断言是**节点数**:上限之外那些必须连节点都没建。
做成 `display:none` 的话,省下的只是重排,建节点那份开销一分没少。

## 快捷键面板:一张不许撒谎的表

快捷键过去只在工具栏上写一行灰字(`↑↓ 翻 r 读完 a 归档`),而且窗口一窄
就整行消失。用户不知道自己漏了什么,也不知道还有没有别的。

现在 `?` 或点那行提示打开一张全表。**清单在 `shortcuts.ts` 里,不在渲染
函数里手写**——手写的话加个新键十有八九忘了回来补。

而表跟代码会分叉,两个方向都坏:

```text
表里有、代码里没有 -> 用户照着按没反应。他不会怪表,只会觉得"有些键不灵"
代码里有、表里没有 -> 那个键等于不存在,做它的那半天白花
```

所以 `shortcuts.test.ts` **拿源码里真实的按键判定去核那张表**(不是再抄
一遍):扫 `e.key === "…"`、`e.key.toLowerCase() === "…"` 和局部变量
`key === "…"` 三种写法,连修饰键一起(`Ctrl`+`V` 写成光 `v` 的话,
用户后面敲的每一个 v 都会被吞掉;反过来面板写「r」而代码判 `Ctrl`+`R`,
用户光按 r 什么也不会发生)。双向都要对上,外加一条
「扫到了判定,不是空跑一趟」盯着这个扫描器自己。

**`keys` 和 `caps` 是两个数组。** `keys` 是 `KeyboardEvent.key` 小写后的值
(`arrowdown`),`caps` 是界面上要显示的键面(`↓`)——同一个字符串没法
两用,而对不上的后果是面板上少显示一个键。

## 「这库里有什么」

存了一个月之后,真正的问题不是"某篇文章在哪儿"——是**这件事到底有没有在做**。
存了九十篇、读完六十篇,和存了九十篇、一篇没读,是两个完全不同的处境,
而列表页对这两个处境显示的是同一屏东西。

`stats.ts` 算四组数:总览(总共/没读过/读了一半/写过批注)、按月、
按站点、按标签。三个判定值得单独记:

```text
**按本地日历月,不是 UTC。** 东八区的 3 月 1 日凌晨,在 UTC 里还是 2 月 28 日。
**空月补零,不跳。** 跳掉没有剪藏的月份,柱子会连成一排——而"三月一篇没存"
恰恰是用户最该看见的那件事,它说明他三月很忙,或者他三月不用这个软件。
**并列的按名字排。** 只按 count 排的话,并列的那些每次渲染顺序都可能变,
用户点开统计页会看见站点那一栏自己在跳。
```

**算的是内存里那份 `clips`,不重扫磁盘。** 面板一打开就等一次全库扫描的话,
用户点它之前得先想"值不值得等";而这一页的意义就在于随手看一眼。
代价是它和磁盘可能差一次刷新的时间——但列表也在内存里,两边一致。

**标签那一栏点了能筛。** 只列数字不给动作的一页等于白做:用户看完
"待读 37 篇"想知道是哪些,这一下点击就是唯一的出路。

**零那一格不画柱子。** 给它留一条底线的话,"这个月一篇没存"和
"这个月存了两篇"在图上长得一模一样。

**时间轴从左到右是旧的新**(`byMonth.reverse()`)。倒过来的话,
柱子读起来是"越来越差",而用户这个月明明比上个月存得多。

## 这一轮变异验证发现的空门

16 处变异,一开始漏了 2 处。两处都不是测试写少了,是**测试写错了对象**:

**`months.includes(month)` 那句过滤是空的。** 轴是按 `months` 铺的,
Map 里多存一个老月份的键,`byMonth` 永远读不到它——改坏那句,测试照样绿。
**那句代码删了**,断言改成测结果(轴上不该出现 2019-03),而不是测那句
过滤有没有执行。

**`snapshotClips` 那条测试传的是 `{ read: false }`**,read 本来就在单子上——
所以"不管三七二十一全拍下来"的改法在它那儿是无差别的。补了一条传
「只归档」的:快照里就**只有** filename 和 archived,多出 read / starred
都算错。

两处的形状一样:**断言要对着"能被观察到的行为",不是对着"我以为在起作用
的那行代码"。** 前者改坏了会红,后者改坏了照样绿——而那正是最容易骗过
自己的地方。
